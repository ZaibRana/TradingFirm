# Spec — Part 3.1: risk-shield service skeleton

Status: **approved 2026-09-09** (chat approval of draft v2, plus the two inline corrections recorded below in decisions 6 and 10). Built as one `feat:` commit plus a follow-up `docs:` commit.

## Spec

Part 3.1 gives `services/risk-shield` the three infrastructure modules the rest of Phase 3 needs — `config.py` (pydantic-settings, mirroring data-engine's shape: service identity, `DATABASE_URL`, `REDIS_URL`, `FRED_API_KEY` as a `SecretStr`, `DEBUG`, and the `asyncpg_url` property), `db.py` (connection pool + `DB_ERRORS`, no table helpers yet) and `cache.py` (Redis connection, one key builder over a `tf:risk:` namespace, TTL constants, the fail-open `cached_json` read-through, and the `tf:risk:health` channel name) — wires them into a lifespan that bounds both connection attempts at 5 seconds each so `GET /health` reports `db_connected` / `redis_connected` instead of a hard-coded `"ok"`, adds migration `005_risk.sql` creating `risk.macro_briefs` (the health tables already exist in `001`), and gives the service a test home: a `dev` Dockerfile stage, `requirements-dev.txt`, `pytest.ini`, and a compose twin `risk-shield-dev` on port 8013 pointed at `tradingfirm_dev` and Redis DB 1 with an empty FRED key. It must **not** call any external API (no yfinance, no FRED — 3.2 is the first part that fetches anything), must not write to any schema other than `risk`, must not read or copy data-engine's modules at import time (copy the pattern, not the code — the two services share no Python package), must not let a missing **or slow** Postgres or Redis stop the service from booting or delay it past ~10 seconds, must not collide with data-engine's `tf:cache:` Redis keys, must not touch the prod database or the prod containers, must not open a socket from any test, and must not let `FRED_API_KEY` or the `DATABASE_URL` password reach a log record, a `repr` or an HTTP response (G14). Acceptance: `005_risk.sql` applies to `tradingfirm_dev` through `scripts/dev-db.sh` and a rerun is a no-op; `docker compose --profile dev up -d risk-shield-dev` boots and `curl :8013/health` returns `db_connected: true, redis_connected: true, fredConfigured: false`; every failure-branch row below has a passing test inside `tf-risk-shield-dev`; prod's `tf-risk-shield` container, the prod database and data-engine's Redis keys are untouched, with the prod migration and the prod recreate listed as waiting for a go (G15).

## Decisions the plan row leaves open

1. **The migration is `005_risk.sql`, not `004_risk.sql`.** The plan row was written before Phase 2 existed; `004_filings.sql` shipped with Part 2.2 and `scripts/migrate.sh` keys `public.schema_migrations` by filename in sorted order, so the number is taken. Recorded in `docs/decisions.md` as a plan correction (plan files are read-only) and noted in `docs/progress.md`.
2. **`risk.macro_briefs` columns are exactly plan §4's**, with the two conventions this repo has settled on added: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `generated_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `regime VARCHAR(20) CHECK (regime IN ('HEALTHY','CAUTIOUS','DANGER','CRITICAL'))` (the same CHECK `risk.health_checks` carries, so one vocabulary), `health_score INTEGER CHECK (health_score >= 0 AND health_score <= 100)`, `brief_text TEXT NOT NULL`, `inputs JSONB NOT NULL DEFAULT '{}'::jsonb`, plus `CREATE INDEX IF NOT EXISTS idx_macro_briefs_generated_at ON risk.macro_briefs(generated_at DESC)` — 3.6's `GET /macro/brief` is "the latest row". **No `user_id`:** D18 puts `user_id` on positions, verdicts and alerts; the macro brief is one shared market view, not a per-user artefact. The file opens with **`CREATE SCHEMA IF NOT EXISTS risk;`** so its rerun guarantee does not depend on `001` having run — free, and it makes the file standalone. `IF NOT EXISTS` on every `CREATE` and no seed `INSERT` (the migration rule).
3. **`db.py` ships the pool and `DB_ERRORS` only — no table helpers.** A writer belongs to the part that uses it: `insert_health_check` / history read land in 3.4, `insert_macro_brief` / `get_latest_brief` in 3.6. `DB_ERRORS = (asyncpg.PostgresError, asyncpg.InterfaceError, ConnectionError)` is copied verbatim from data-engine **including the reason `OSError` is absent** (Part 2.4: `asyncio.TimeoutError` subclasses `OSError`, so an `OSError`-based tuple reports every timed-out call as a dead database).
4. **Redis namespace is `tf:risk:`, not `tf:cache:`.** Both services share Redis DB 0 in prod, and data-engine owns `tf:cache:*`. One key builder, `cache.risk_key(kind, name="")` → `tf:risk:cache:{kind}[:{name}]`, and one normalizer, `cache.canonical(name)` (strip + upper), which every key builder in Phase 3 calls — quotes keys, FRED series keys (`DGS10`, `VIXCLS`) and the health snapshot key all go through it (G1.5). The pub/sub channel `tf:risk:health` (plan 3.4) is a constant here so 3.4 does not invent a second spelling. TTL constants shipped now, unused until their part: `TTL_QUOTES = 300` (3.2), `TTL_FRED = 21600` (3.2, 6 h), `TTL_HEALTH = 300` (3.4).
5. **`cached_json` is copied, not imported.** The same read-through contract as data-engine's (`(body, from_cache)`, fail-open on a `None` client and on a raising get/set, a `valid` shape check that turns a wrong-shaped hit into a miss, a raise inside `fetch()` propagating and caching nothing) minus the `ttl_for` hook, which only the dossier needs. Copying is the plan row's instruction ("copy pattern, not code"); the two services have separate images and no shared package, so an import is not available anyway.
6. **Lifespan: fail-open, and bounded — a deliberate addition, not a mirror.** Redis and Postgres are each tried in a `try/except`, a failure logs a warning and leaves `app.state.redis` / `app.state.db_pool` as `None`, and the service still boots. Fail-open is only true if the attempt *returns*, and neither default does: `asyncpg.create_pool()` opens `min_size` connections with a 60 s default connect timeout (data-engine's `command_timeout=30` bounds queries, not connection establishment), and redis-py's `socket_connect_timeout` defaults to `None` — unbounded. A Postgres that is restarting rather than refusing would therefore stall `tf-risk-shield` startup for a minute with `/health` unreachable, the opposite of what fail-open promises. So this part bounds both:
   - `db.create_db_pool(timeout=5.0)` passes `timeout=5.0` to `asyncpg.create_pool` **and** the lifespan wraps the whole call in `asyncio.wait_for(..., 5.0)` — the pool opens `min_size=2` connections, so the per-connection timeout alone allows ~2× the bound; the outer `wait_for` is the hard one. Pool settings otherwise mirror data-engine: `min_size=2, max_size=10, command_timeout=30`.
   - `cache.create_redis(timeout=5.0)` passes `socket_connect_timeout=5.0, socket_timeout=5.0` to `from_url`, and the lifespan wraps **`create_redis()` and its `PING` together** in one `asyncio.wait_for(..., config.STARTUP_TIMEOUT)`. **Correction made during commit 1** (review of draft v2): v2 wrapped only the `PING`, which left the factory call itself unbounded — and `test_lifespan_redis_slow_times_out_and_boots` patches `create_redis` to hang, so as specified that test would have hung forever rather than proving the bound. The Redis side now mirrors the DB side exactly: one `wait_for` around the whole attempt.
   - **Worst-case boot ≈ 10 s** (5 + 5, sequential), inside the container's `HEALTHCHECK --start-period=10s --retries=3` (first failure at ~20 s, restart never triggered by a slow dependency alone). A timeout is `TimeoutError`, caught by the same `except Exception` and reported exactly like a refusal: warning + `None`.
   - `STARTUP_TIMEOUT = 5.0` is a module constant in `config.py` so 3.4's scheduler and any later service reuse the number rather than re-deriving it. **It is read at call time as `config.STARTUP_TIMEOUT` inside the lifespan, never bound with `from config import STARTUP_TIMEOUT` at import** — a `from`-import copies the value into `main`'s namespace, so the slow-path tests' monkeypatch would not land and each would sit for the full 5 s (or fail outright). Every later part that bounds a wait reads it the same way (3.4's scheduler included). Data-engine is left unchanged here — a bounded startup there is a separate `refactor:`, noted in `docs/decisions.md`, not smuggled into a Phase 3 feature part.
   No scheduler task in this part (3.4).
7. **`/health` fields are boot state, mirroring data-engine, and this is stated as a limitation.** `db_connected = app.state.db_pool is not None` and `redis_connected = app.state.redis is not None` — the outcome of the startup attempt, exactly data-engine's `main.py:258-259`. **No live `SELECT 1` / `PING` per request**, so no "up at boot, down at request time" row is needed and none is claimed: a dependency that dies after boot still reports `true` until the service restarts. That is a known, shared limitation of both services; a probing `/health` (and the reconnect logic it would imply) belongs to its own part, recorded as deferred in `docs/progress.md`. `/health` also gains `fredConfigured` (a boolean from `bool(settings.fred_api_key.get_secret_value())`, never the key — G14) and bumps `version` `0.1.0` → `0.2.0`. `GET /` keeps its shape and lists the endpoints as data-engine's does.
8. **`FRED_API_KEY` is wired to prod compose only; the dev twin hard-codes it empty**, the pattern 2.1/2.2/2.3 set for every key. It is already present and blank in `.env.example` (Part 0.1), so no `.env.example` change. Nothing in 3.1 reads it beyond reporting the boolean.
9. **A dev twin now, not later** (addition to the plan row, same shape as Part 0.7's `data-engine-dev`). The plan row names `tests/test_config.py` but Phase 3 has no place to run pytest: the prod image has no test deps and the host Python is not the pinned set. So: a `dev` Dockerfile stage (base + `requirements-dev.txt`, no `COPY . .`, image inert without the source mount), `requirements-dev.txt` (`-r requirements.txt`, **`pytest==9.1.1`, `pytest-asyncio==1.4.0` — the exact versions in `services/data-engine/requirements-dev.txt`, so the two twins cannot drift**; no `respx`, since 3.1 makes no HTTP call — 3.2 adds it at data-engine's pin), `pytest.ini` (`testpaths = tests`, `python_files = test_*.py`), and compose service `risk-shield-dev` (profile `dev`, container `tf-risk-shield-dev`, port **8013**→8003, source volume-mounted, `./infra/supabase/migrations:/migrations:ro` mounted for decision 10's file-level migration tests, `DATABASE_URL` → `tradingfirm_dev`, `REDIS_URL` → `redis://redis:6379/1`, `FRED_API_KEY: ""`, `DEBUG: "true"`, `restart: "no"`, no `depends_on`). `scripts/dev-db.sh` needs no change: it applies every migration in the directory to `tradingfirm_dev`. The prod stage stays last so `docker compose build risk-shield` still gets it.
10. **Tests: five files, all offline, no socket — and the split between lifespan tests and stubbed-state tests is explicit.**
    - `tests/test_config.py` — defaults, env override, `asyncpg_url`, `SecretStr` behaviour.
    - `tests/test_cache.py` — key builder, normalizer, and every `cached_json` branch against an in-process fake Redis (`tests/fake_redis.py`, the Part 1.7 pattern, copied).
    - `tests/test_db.py` — `DB_ERRORS` membership (incl. the `OSError`/`TimeoutError` regression), and `create_db_pool` with `asyncpg.create_pool` patched: stripped DSN, pinned sizes, `timeout=5.0`, and the log record carrying no password.
    - `tests/test_lifespan.py` — **the real lifespan runs** (`with TestClient(app) as c:`) with `db.create_db_pool` and `cache.create_redis` patched at their module attribute, and `config.STARTUP_TIMEOUT` monkeypatched down to a fraction of a second for the slow rows (which is why `main.py` reads it as `config.STARTUP_TIMEOUT` at call time — decision 6). Covers failure rows 1–4 and 6–7: each patched to raise, to hang past the bound (an `asyncio.sleep` longer than a monkeypatched-down `STARTUP_TIMEOUT`, so the test is fast), or both; each asserts the `caplog` warning record, `app.state.X is None`, and `/health` 200 with the right boolean. The both-up lifespan case is here too, with both factories patched to return fakes.
    - `tests/test_health.py` — the response-shape tests only, over `TestClient` with **stubbed** `app.state` (no lifespan): `fredConfigured` true/false and the key-never-leaks assertion, `GET /` shape, `version`. Stubbing is correct here because these assert serialization, not startup.
    - `tests/test_migration.py` — **file-level text assertions only, option (a)**: parses `/migrations/005_risk.sql` (the read-only mount from decision 9; path from `MIGRATIONS_DIR`, default `/migrations`) and asserts the schema/table/index/CHECKs are present, every `CREATE` carries `IF NOT EXISTS`, and no `INSERT` appears. **It does not connect to Postgres.** The real apply-and-rerun is not a test at all: it is the `scripts/dev-db.sh` acceptance step in Verification below, whose output goes in the completion report.
11. **G15 — nothing runs against prod in this part.** Verification is the dev twin and `tradingfirm_dev` only. Two prod actions stay queued for the completion report: `./scripts/migrate.sh` and `docker compose up -d --build risk-shield`.
12. **Commits: `feat:` then `docs:`.** `feat: risk-shield service skeleton` carries the spec file, the code, the tests, the migration, the compose/Dockerfile changes and the `docs/decisions.md` entries (005 renumber, bounded startup, the unbounded-startup note for data-engine) — tests never ride in a `docs:` commit. The follow-up `docs:` commit carries the `docs/progress.md` row and the `docs/overview.md` update, which need the `feat:` hash. The completion report states **authored vs collected** test counts and ends with `git diff --stat 536aecf..HEAD`. Estimated ~450 new lines, under the 600 split threshold.
13. **Secrets by construction, not by discipline.** `fred_api_key: SecretStr = SecretStr("")` in `config.py`, so `repr(settings)` and `str(settings.fred_api_key)` render `**********` and only an explicit `.get_secret_value()` can produce the key — a leak now needs a deliberate call, not a forgotten f-string. `database_url` stays a plain `str` (the `asyncpg_url` property and asyncpg both need the raw value), guarded the way data-engine guards it: the startup log prints only the half after `@`. `test_create_db_pool_logs_dsn_without_password` uses a DSN with a distinctive password and asserts that string appears in no `caplog` record at any level; `test_health_fred_configured_never_leaks_key` does the same for a distinctive key across `/health`, `/` and the logs, which also exercises the `SecretStr` path.

## Writes

| write | before / after success | state left if it fails after |
|---|---|---|
| Postgres schema `risk`: `CREATE SCHEMA IF NOT EXISTS` + table `macro_briefs` + index, via `005_risk.sql` applied by `scripts/dev-db.sh` to `tradingfirm_dev` | absent / present, empty | `psql -v ON_ERROR_STOP=1` aborts the file; `migrate.sh` records the filename only after the file succeeds, so a rerun re-applies it; every statement is `IF NOT EXISTS`, so a partial apply heals on rerun |
| `public.schema_migrations` row `005_risk.sql` (dev database only in this part) | absent / present | inserted after the file applies; a crash between the two leaves the file re-applied next run — a no-op by construction |
| Redis | **n/a** — 3.1 defines keys and TTLs but writes none. The only Redis traffic is the startup `PING` | n/a |
| `app.state.db_pool` / `app.state.redis` (process memory) | unset / pool + client, or `None` when the dependency is down, refusing or slower than 5 s | `None`, `/health` reports `false`, the service still serves |
| Docker image `risk-shield` `dev` stage + container `tf-risk-shield-dev` | absent / built and running on 8013 | prod `tf-risk-shield` is a different container and a different stage; a failed dev build leaves it running |

## Spec

Part 3.2 gives risk-shield its two market inputs: `monitors/quotes.py` makes **one** `yf.download` of the plan's 17 core tickers (daily, 1y) and caches a JSON body in Redis for 5 minutes. `monitors/fred.py`, over a thin typed `monitors/fred_client.py`, fetches the plan's 8 FRED series one request each and caches each for 6 hours. Both sit behind source-wide cooldowns copied from data-engine's `cache.py` (`MemoryCooldowns` / `cooldown_remaining` / `start_cooldown`, under `tf:risk:cooldown:`) and an in-process rate limiter copied from data-engine's `ratelimit.py`.

It must **not**:
- return `None` into `cached_json` (every fetcher returns an envelope with a `reason`, and `cached_json` itself now refuses a `None`)
- cache a degraded body (`reason` not null) for longer than 120 s
- retry anything, or send a request while its source is cooling down
- let one bad FRED series block the others
- write to Postgres or to any Redis key outside `tf:risk:`
- let the FRED key reach a log record, an exception message or an HTTP response (G14)
- call yfinance, FRED, Postgres or Redis from a test
- add an endpoint, a scheduler or a lifespan change (all 3.4)
- touch the prod container, the prod image tag or the prod database

Acceptance:
- every failure-branch row below has a passing test in `tf-risk-shield-dev`, with the dev twin rebuilt on the new pins
- the FRED live canary (1 series, then all 8) and the quotes canary (SPY, then the 17) each ran exactly once in a throwaway container isolated from prod Postgres and Redis, and their actual output is in the completion report
- any error, refusal, empty result or unexpected shape during a live run stops the run and is reported under G3.5 (root cause + two options) before anything is changed
- prod is untouched

## Decisions the plan row leaves open

1. **Envelopes, never `None`, never a bare `{}`.** Every cached body is a dict with a `reason` field.
   - **Quotes:** `{asOf, period: "1y", interval: "1d", tickers: {SPY: {date[], open[], high[], low[], close[], volume[]}, …}, missing: [...], reason: null | "partial" | "empty"}`. Columnar per ticker, dates as `YYYY-MM-DD`, NaN → `null`, rows with a NaN close dropped.
   - **FRED:** `{seriesId, asOf, observationStart, observations: [{date, value}], dropped: n, reason: null | "empty"}`.
   - **Why not a bare `{}` / `[]`:** the `valid` predicate would reject it as the wrong shape, and it would be refetched on every call. That is the same G6 trap as a stored `null`, just by a different route.
   - **`valid` predicates:**
     - Quotes: required keys present; `reason` in the allowed set; `set(tickers) ∪ set(missing) == set(CORE_TICKERS)`, so a body cached before a ticker-list change is a miss.
     - FRED: `seriesId` equals the requested canonical id; `observations` is a list; `reason` in the allowed set.
2. **A stored `null` is a miss that heals itself, and `cached_json` can no longer write one.**
   - **Reading a stored `null`:** `get_cached_json` returns `None` for a JSON `null`, so `cached_json` treats it as a miss. `fetch()` runs and the key is overwritten with an envelope. The next call is a hit, so a stored `null` costs at most one extra fetch, never one per call. Test: `test_cached_json_stored_null_is_miss_and_overwritten` asserts fetch count 1 across two calls.
   - **New guard in 3.1's `cached_json`:** if `fetch()` returns `None`, it raises `TypeError` and caches nothing. This fails closed, because a `None` from a fetcher is a bug and not an answer. Test: `test_cached_json_fetch_returning_none_raises_and_caches_nothing`.
3. **Refusal raises; an answer is cached, and a degraded answer only briefly.** This is data-engine's 2.4 split.
   - **A refusal** (rate limit, lock, bad key) raises a typed error, starts the source's cooldown and caches nothing.
   - **An active cooldown** raises `…CoolingDown(remaining)` before any request and caches nothing. A cache hit is still served while a source cools down. Order: cache read → cooldown check → request.
   - **A full answer** (`reason: null`) caches for the normal TTL: `TTL_QUOTES = 300`, `TTL_FRED = 21600`.
   - **A degraded answer** (`reason` not null: `"empty"`, and `"partial"` for quotes) caches for **`TTL_DEGRADED = 120`**, the value data-engine uses for a dossier with a failed section (`TTL_DOSSIER_ERROR`). One transient empty FRED response therefore blanks `DGS10` for two minutes, not six hours. The short TTL still keeps the cache between the source and a tight loop.
   - **Mechanism:** the `ttl_for` hook dropped in 3.1 is restored in `cached_json`, copied from data-engine `cache.py:315` including "`ttl_for` wins over `ttl`". Each source passes a body-derived function, `quotes_ttl(body)` / `fred_ttl(body)` → `TTL_DEGRADED if body["reason"] is not None else` the normal TTL.
   - **Cooldown interaction:** the all-17-empty cooldown (decision 6) still starts as specified. After the 120 s body expires, the next call hits the 900 s cooldown and raises with no request.
4. **Cooldowns are copied from data-engine `cache.py` (lines 123–202) with the same semantics.**
   - **What is copied:** `MemoryCooldowns` (`remaining(name, ttl)`, `start(name)`); `cooldown_remaining(r, memory, name, ttl)` (Redis `TTL` is the source of truth, a raise or `r is None` falls back to memory, no memory means clear); `start_cooldown(r, memory, name, ttl)` (Redis `SET … EX`, a raise falls back to memory).
   - **Source-wide:** one name per source (`SOURCE_YFINANCE = "yfinance"`, `SOURCE_FRED = "fred"`), never per ticker or per series. A 429 on `DGS10` blocks `VIXCLS`.
   - **The one difference is the key:** `cooldown_key(name)` → `tf:risk:cooldown:{canonical(name)}` (for example `tf:risk:cooldown:FRED`). `canonical()` is still the only normalizer (G1.5), and nothing lands under data-engine's `tf:cache:`.
   - **TTLs:**

     | constant | seconds | when it starts |
     |---|---|---|
     | `TTL_COOLDOWN_YFINANCE` | 900 | a rate limit, or the whole download coming back empty |
     | `TTL_COOLDOWN_FRED` | 900 | 429 / 423 |
     | `TTL_COOLDOWN_FRED_AUTH` | 3600 | a 400 naming `api_key` |

   - **Correction made during commit 2:** the copied `MemoryCooldowns` stores only a start time, and its check needs one TTL. With Redis absent it therefore cannot tell a 429 (900 s) from a bad key (3600 s). `monitors/fred.py` checks it with `TTL_COOLDOWN_FRED`, so in memory-only mode a not-authorized refusal is remembered for 900 s. The Redis path keeps the real TTL of whichever cooldown was set.
   - **Where the memory clock lives in 3.2:** fetchers take `r` and `memory` as arguments. `app.state.cooldowns` is wired in 3.4 together with the first caller; `main.py` is unchanged in this part.
5. **Core tickers, the quotes download, its request count and its worst case.**
   - `CORE_TICKERS` is the plan's 17 in plan order: `SPY QQQ RSP ^VIX TLT GLD UUP XLK XLU XLP XLV XLY XLF ES=F NQ=F CL=F GC=F`. Each goes through `canonical()`; the list is ≤ 20 per download.
   - **The call:** `yf.download(" ".join(CORE_TICKERS), period="1y", interval="1d", group_by="ticker", threads=False, progress=False, auto_adjust=True, timeout=5)`, run through `asyncio.to_thread`, with no `session=`.
   - **Request count, from the installed 1.5.1 source:** with `threads=False`, `download` loops `Ticker(t).history()` once per ticker (`multi.py`). Each `history()` first calls `_get_ticker_tz(timeout=10)` (`base.py:135`). That makes a network request unless the ticker's timezone is in yfinance's on-disk cache (`user_cache_dir()/py-yfinance`, inside the container's filesystem).
     - **Cold** (a new or recreated container, and every throwaway canary): 17 timezone + 17 history requests = **34 requests**.
     - **Warm** (later downloads in the same container): **17 requests**.
     - Plan §2's ~80 downloads/day is therefore ~1,360 requests/day warm, plus 17 once per container start. The single-download design approved on v1 stands; this corrects the count.
   - **Timeouts and worst case.** yfinance's `timeout` covers only the history request. The timezone timeout is hard-coded at 10 s and cannot be passed through.

     | per-request `timeout` | cold worst case | warm worst case |
     |---|---|---|
     | 10 (1.5.1 default) | 17 × (10 + 10) = **340 s**, longer than 3.4's 300 s cadence | 17 × 10 = 170 s |
     | **5 (chosen)** | 17 × (10 + 5) = **255 s**, inside the cadence | 17 × 5 = **85 s** |

     Lowered to 5 s because 340 s would let one cold download overrun the next scheduled check. A 1y daily chart body is tens of kilobytes, so a healthy answer is far below 5 s; a spurious timeout shows up as `reason: "partial"` and caches for only 120 s.
   - **No outer bound, on purpose.** The download runs in a thread, and a thread cannot be cancelled. An `asyncio.wait_for` would only orphan it: the `await` would return, the single-flight lock would be released, and a second download could start while the first thread is still sending requests. That is exactly what the lock exists to prevent.
     - The lock is therefore held until the thread returns.
     - A concurrent caller waits at most the worst case above, then gets the cached body.
     - Acceptable because the worst case (255 s cold, 85 s warm) is under 3.4's 5-minute cadence.
     - Carried to 3.4 as a design constraint: a scheduler tick that finds the lock held skips rather than queues, and cadence never drops below the cold worst case.
   - **Single-flight:** a module-level `asyncio.Lock` wraps `cached_json`, so concurrent misses make one download and the second caller finds the cached body. **Correction made during commit 3:** it is one lock per running event loop (`quotes._download_lock()`), not a single module-level `asyncio.Lock`. A lock binds to the first loop it waits on, and pytest runs each test on a new loop; the service runs one loop, so it still gets exactly one lock.
   - **Frame → envelope:** handles MultiIndex `(Ticker, Price)` and flat columns, then `del df` + `gc.collect()` (G8).
   - **Version guard:** the detection in decision 6 relies on 1.5.1's log format, so `yf.__version__ != "1.5.1"` raises `QuotesError` before any request.
6. **How a yfinance refusal is detected.** In 1.5.1, `download` catches every per-ticker exception, `YFRateLimitError` included, into a local `ctx.errors` and only logs it. The two log formats that can carry a refusal:
   - the download summary: `['SPY']: YFRateLimitError('Too Many Requests. Rate limited. Try after a while.')` (`multi.py`)
   - the timezone fetch: `Failed to get ticker 'SPY' reason: YFRateLimitError(…)` (`base.py`)

   `shared._ERRORS` is never written. The rules:
   - **Log capture:** a temporary `logging.Handler` sits on `logging.getLogger("yfinance")` for the duration of the download and is removed in `finally`. Any record matching `YFRateLimitError|Too Many Requests` means `QuotesRateLimited`: start the cooldown, discard the frame, cache nothing.
   - **A raised `YFRateLimitError`** is treated the same way.
   - **Any other raise** → `QuotesError`, no cooldown, nothing cached.
   - **All 17 empty with no rate-limit record** → envelope `reason: "empty"`, cached 120 s, **and** the 900 s cooldown is started (1.x's silent-block pattern).
   - **Some tickers empty** → `reason: "partial"`, with those tickers in `missing`, cached 120 s, no cooldown.
7. **FRED: the endpoint, the key and the timeout.**
   - **Verified today** against `fred.stlouisfed.org/docs/api/fred/series_observations.html` and `/errors.html`:
     - URL `https://api.stlouisfed.org/fred/series/observations`
     - `api_key` is a **query parameter only**
     - `file_type=json`; observations carry `date` and `value`
     - errors come back as JSON `{error_code, error_message}` with 400 / 404 / 423 / 429 / 500
     - the limit is **120 requests per minute**
   - **Key in the query string (approved on v1)**, on the two Alpha Vantage conditions, both held in `fred_client.py`:
     - the `httpx` logger is pinned to WARNING
     - every typed error is raised `from None`, with a message built from the series id and the HTTP status or `timeout` only. `error_message` is inspected for `api_key`, never formatted; `resp.url` is never logged.
   - Recorded in `docs/decisions.md`; CLAUDE.md gets a FRED line beside the Alpha Vantage one.
   - **Request:** `series_id`, `api_key`, `file_type=json`, `observation_start = today(UTC) − 800 days`, `sort_order=asc`. `today` is an injectable callable on the client, so tests freeze it.
   - **Timeout: 8 s per request.** The number is data-engine's per-source bound (`SECTION_TIMEOUT = 8.0`, `dossier/assemble.py:89`); its HTTP clients themselves use 10 s. Applied twice:
     - `httpx.AsyncClient(timeout=8.0)`, which in httpx bounds each phase (connect, write, pool, and each read) separately rather than the whole request
     - `asyncio.wait_for(…, FRED_REQUEST_TIMEOUT)` around the whole request, which is the hard bound. This is safe here, unlike quotes, because an httpx request is a coroutine and cancels cleanly.

     A timeout raises `FredError` (`"{series}: timeout"`).
   - **Error mapping:**

     | response | typed error | base |
     |---|---|---|
     | empty key | `FredNotConfigured`, before any request, no cooldown | `FredSourceWide` |
     | active cooldown | `FredCoolingDown`, before any request | `FredSourceWide` |
     | 429, 423 | `FredRateLimited` | `FredSourceWide` |
     | 400 whose `error_message` contains `api_key` | `FredNotAuthorized` | `FredSourceWide` |
     | any other 4xx / 5xx, timeout, transport error, `OSError`, non-JSON, or 200 without an `observations` list | `FredError` | — |

     `FredSourceWide(FredError)` is the marker base decision 8 branches on.
   - **Allowlist:** `FRED_SERIES = VIXCLS DGS10 DGS2 T10Y2Y DFF DCOILWTICO CPIAUCSL UNRATE`. An id outside it, after `canonical()`, raises `ValueError` before any request.
   - **Missing values:** `"."` or anything else non-numeric is dropped and counted in `dropped`.
8. **FRED limiter, snapshot and worst case.**
   - **Limiter:** `ratelimit.py` copies data-engine's `RateLimiter` (injectable clock and sleep). One module-level `fred_limiter = RateLimiter(max_calls=60, window=60.0, min_gap=1.0)`: half FRED's cap, and ≥ 1 s between calls. Same one-uvicorn-worker assumption as data-engine.
   - **`fred_snapshot(r, memory, client)`** walks the 8 series in order. A source-wide state stops the walk; a per-series error does not:
     - **`FredSourceWide`** (`FredCoolingDown`, `FredRateLimited`, `FredNotAuthorized`, `FredNotConfigured`): that series gets its status (`cooldown` / `rate_limited` / `not_authorized` / `unconfigured`), the walk **stops**, and every remaining series is `skipped` with no request. The state is true for the whole source, so another request would be refused or wasted.
     - **`FredError`** (a 404, a 5xx, a timeout, a shape change): that series is `error`, and the walk **continues** to the next series. Because the walk is in fixed order, stopping here would let one persistently broken series blank every series after it indefinitely.
   - **It returns** (not cached; each series is) `{SERIES: {status, cached, observations, dropped}}`, with `status` ∈ `ok | empty | cooldown | rate_limited | not_authorized | unconfigured | error | skipped`. On failure `observations: []`, never `None`.
   - **Worst case, cold walk:** every series times out, which is a per-series `FredError`, so the walk continues: 8 × 8 s + 7 × 1 s gap = **71 s (≈ 72 s)**. Errors are not cached, so a full FRED outage costs ~72 s on every snapshot call. That is under 3.4's 5-minute cadence; 3.4 must not call the snapshot more often than that.
   - **Normal cost:** 8 requests cold, ~8 s, then 0 for 6 h; ≤ 32/day.

## Writes

| write | before / after success | state left if it fails after |
|---|---|---|
| Redis `tf:risk:cache:quotes` | set after a non-refused download: TTL 300 when `reason: null`, **120** when `partial` / `empty` | a `SET` raise is logged and the body is still returned; nothing cached, so the next call downloads again (bounded by the lock and 3.4's cadence) |
| Redis `tf:risk:cache:fred:{SERIES}` | set after a 200 with an `observations` list: TTL 21600 when `reason: null`, **120** when `empty` | same, per series |
| Redis `tf:risk:cooldown:YFINANCE`, TTL 900 | set **after** a detected rate limit, or after an all-empty download | a `SET` raise falls back to `MemoryCooldowns.start` |
| Redis `tf:risk:cooldown:FRED`, TTL 900 / 3600 | set **after** 429 / 423, or after a 400 naming `api_key` | same fallback |
| `MemoryCooldowns` (process memory) | written only when Redis is `None` or raising | lost on restart: a restart forgets a refusal (data-engine has the same limit) |
| yfinance timezone cache (container filesystem) | written by yfinance itself on the first download | lost on container recreate; the next download is cold again (34 requests) |
| Postgres | **n/a**, nothing written | n/a |
| image `tradingfirm-risk-shield-dev` + container `tf-risk-shield-dev` | rebuilt with the new pins | a failed build leaves the previous dev image; the prod tag is untouched |
| files from the canaries | **n/a**, they write none (yfinance's timezone cache dies with the `--rm` container) | n/a |

## Carried forward (design constraints, not built here)

**To 3.3:**
- **`…CoolingDown` is stale, not an error.** Once a degraded body's 120 s expires during an active cooldown, the fetcher raises `QuotesCoolingDown` / `FredCoolingDown`. 3.3's monitors must answer that with `stale: true` and the last known body, not an error. 3.3's spec starts from this.

**To 3.4:**
- A scheduler tick that finds the quotes lock held skips rather than queues.
- Cadence stays ≥ the quotes cold worst case (255 s) and the FRED outage walk (~72 s).
- `app.state.cooldowns` is wired together with the first caller.
- **The yfinance timezone cache is per container.** The 34-request cold start recurs every time a prod container is recreated, which happens on every rebuild. 3.4, or its deploy step, decides between a named volume for yfinance's cache dir (so a recreate costs no extra 17 requests) and explicitly accepting the cost. Decided there, not here.

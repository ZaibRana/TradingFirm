# Spec — Part 2.3: Earnings dates + reaction history

Status: **approved 2026-09-09** (chat approval of draft v2 plus the corrections folded in below; decision 13 approved under two conditions, recorded there). Built as two feat commits under this one spec.

## Spec

`earnings_reaction_history(pool, ticker, limit=8)` returns the last 8 confirmed earnings reports for a ticker with the reaction the stock printed on each (opening gap % and close-to-close %), computed by a pure function from `data_engine.events` rows of type `earnings` joined by calendar date to stored daily bars, plus `dataQuality: {source, dropped, disagreements}`; the report dates are fetched during `POST /stock/{ticker}/refresh` from yfinance `Ticker.get_earnings_dates(limit=12)` as primary and from Alpha Vantage `EARNINGS` as fallback when the primary raises a non-rate-limit error, returns no past rows, or has no past row that survives validation, and are stored with `meta.earnings.{source, validated, hour, epsEstimate, epsReported, surprisePct}`. It must never fall back on a rate limit (`yfinance.exceptions.YFRateLimitError` → `ProviderRateLimited`; the step stops and the refresh still returns 200), never call the fallback when validation was impossible because the bar store is empty, never store a past report date that is not a stored bar date or adjacent to one, never resolve an unknown report hour or a cross-source disagreement by anything other than the volume rule (`calc_rvol ≥ 2` on the same or next session), never let the earnings step fail a refresh whose bars were stored, never call yfinance, Alpha Vantage or Postgres from a test, and never let the Alpha Vantage key reach a log record at any level. Acceptance: live canaries (yfinance one ticker then two more, Alpha Vantage one ticker; four external calls in total) print shapes and column names only; fixtures for AAPL / MSFT / SPY (yfinance) and AAPL (Alpha Vantage) are recorded; every failure-branch row below has a passing test; the AAPL end-to-end test yields hand-checked gap and close-to-close numbers for at least three real reports; the prod container and prod database are untouched.

## Decisions

1. **Sources and order.** Primary: the data provider's new `get_earnings_dates(ticker) -> pd.DataFrame | None` (yfinance provider: one `Ticker(t).get_earnings_dates(limit=12)` after `YF_INFO_DELAY`, no `session=`, no retries; fixture provider: `tests/fixtures/earnings_dates/<T>.json`, where `SPY.json` holds the literal `null` because yfinance returns `None` for an ETF, and a *missing* file raises `FileNotFoundError` = never recorded). Fallback: `providers/context/alphavantage_client.py` + `alphavantage_earnings()` in `providers/context/earnings.py`, `GET /query?function=EARNINGS&symbol=<T>`, using `quarterlyEarnings[].reportedDate` (+ `reportTime`, `reportedEPS`, `estimatedEPS`, `surprisePercentage`). Key: `settings.alphavantage_api_key` from `ALPHAVANTAGE_API_KEY`, prod compose only, dev twin hard-coded empty (`AlphaVantageNotConfigured` before any HTTP, counts as down).
2. **Fallback triggers** (`sync_earnings_dates`): the primary raises a non-rate-limit error, returns `None`, returns a zero-row frame, returns only future rows (fresh IPO: zero past rows after the `≤ today` filter), or zero past rows survive validation. Partial survivors do not trigger it. **Never on a rate limit:** `yfinance.exceptions.YFRateLimitError` (confirmed present on the pinned 1.5.1 by introspection, re-confirmed in the canary) — and, belt-and-braces, a message matching rate/too many/429 — is re-raised by the provider as `providers.base.ProviderRateLimited`; the sync stops, stores nothing, warns, `reason: "rate_limited"`. **Never when validation was impossible:** an empty bar store is our failure, not the source's, so an Alpha Vantage call there is wasted — store nothing, `reason: "no_bars"`, no fallback call. Alpha Vantage's `AlphaVantageRateLimited` (`Note` body, per-minute) and `AlphaVantageCapped` (HTTP 200 with an `Information` body = the free daily cap) both count as down; nothing further is tried.
3. **Validation, both sources, at write time.** A past report date is valid when it equals a stored daily bar date or is within one calendar day of one. The bar dates come from **the store, not the refresh frame**: the refresh downloads `period="2y"` while `limit=12` reaches ~3 years back, so validating against the frame would drop older reports the store can still explain. One `db.get_bars(pool, ticker, "1d")` with no `since` at the top of the sync — the whole stored daily history, a superset of `since = oldest report date` and free of the ordering problem that a per-source `since` would create (the oldest date is not known until a source has answered). Rows that fail are not stored and counted in `dropped`. Future dates cannot be validated: stored with `meta.earnings.validated: false` (6.4 needs the upcoming date). Past dates that pass: `validated: true`. **Correction made during commit 1** (from the live data, recorded in `docs/decisions.md`): a past date *older than the whole stored bar history* is counted as `out_of_range`, not `dropped` — it can never be explained by bars we hold, so it is not a data-quality signal. The live AAPL feed returns 25 rows over six years against a two-year store, which would otherwise report `dropped: 20` on a healthy ticker. `validate_report_dates` returns `(kept, dropped, out_of_range)`; `out_of_range` is logged and reaches no response. It is not a `dataQuality` field: the write side's response object is `earningsDates: {source, stored, dropped, reason}`, and the read side's `dataQuality` has exactly `{source, dropped, disagreements}`. **Correction made after commit 2** (`fix:` commit): the read side now treats a report older than the first stored bar the same way — logged, skipped, uncounted — so `dropped` means one thing on both sides, "the source gave us something we could not use". Our bar history being short is not a source-quality problem.
4. **Two separate tolerances, not one.** (a) Rule 3 is about the *report date*: is it a trading day we hold, or adjacent to one. (b) The *reaction session* rule in the pure function: the first bar on/after the expected session, at most 4 calendar days later (holiday weekend); beyond that it is a bar-store gap, skipped and counted. Both stand; they answer different questions.
5. **Report hour.** `meta.earnings.hour` ∈ `amc` / `bmo` / `dmh` / null. yfinance: from the Eastern time of the index (≥ 16:00 → `amc`, < 09:30 → `bmo`, else `dmh`); Alpha Vantage: `reportTime` `post-market` → `amc`, `pre-market` → `bmo`, else null. `amc` → the bar after the report date; `bmo` / `dmh` → the bar on it. **Correction made during commit 2:** the hour falls back to `meta.calendar.hour` for Part 2.1 rows, which carry no `meta.earnings` — without it every legacy row would go through the volume rule and be dropped. **Unknown hour → volume rule:** the candidates are the report-date bar and the next bar; keep the one whose `indicators.calc_rvol(volumes of the 20 bars before it, that bar's volume)` is ≥ 2; exactly one qualifies → used, `hourAssumed: true`; neither or both → dropped and counted. (No "larger absolute gap": that selects the bigger move by construction.)
6. **Cross-source disagreement (read time, pure function).** Rows carry their source; the PK is the date, so two sources naming different dates for one report exist as two rows. **≤ 1 day apart:** one report, collapsed to the primary-source (`yfinance`) row — not a disagreement, not a drop. **> 1 and < 20 days apart:** a disagreement, resolved by the same volume rule applied to each candidate date's session (same day or next): exactly one date qualifies → kept, the other skipped; neither or both → unresolved, both skipped. Every disagreement is counted in `dataQuality.disagreements` and logged with both dates and sources. **Within one source,** two confirmed dates < 20 days apart are the same report (quarters are ≥ 60 days apart): keep the earlier, warn, not a disagreement.
7. **Confirmed reports only** at read time: `meta.earnings.validated` is true, or (2.1 rows that predate this part) `meta.calendar.epsActual` is not null. A bare Finnhub projection is skipped.
8. **Two layers.** Pure `earnings_reactions(events, bars, limit=8, today=None) -> {reactions, dataQuality}` in `indicators/earnings.py`, exported from `indicators.__all__` (22 → 23). I/O in `providers/context/earnings.py`: `sync_earnings_dates(provider, av_client, ticker, pool, today=None)`, the converters `earnings_events_from_df` / `earnings_events_from_av`, `validate_report_dates`, and `earnings_reaction_history(pool, ticker, limit=8, today=None)`.
9. **"One query" reading (read side).** One new generic `db.get_events(pool, ticker, event_type=None, since=None, until=None)` (ascending, `meta` decoded from jsonb text, malformed → `{}` with a warning) plus the existing `get_bars("1d", since=)`. No SQL `LIMIT`: `since = today − 3 y`; the pure function trims. `get_events` is what 2.4 and 6.4 reuse.
10. **Numbers.** `gapPct = (open_r − close_prev) / close_prev × 100` (the `indicators.gap()` formula on the two bars), `closeToClosePct = (close_r − close_prev) / close_prev × 100`, 2 dp. Row: `reportDate`, `session`, `hour`, `hourAssumed`, `source`, `gapPct`, `closeToClosePct`, `epsEstimate`, `epsReported`, `surprisePct`. Newest first. No summary block (2.4 averages what it needs).
11. **Read result shape.** `{"ticker", "reactions": [...] | null, "dataQuality": {"source": "yfinance" | "alphavantage" | "mixed" | null, "dropped": n, "disagreements": n}}`. `reactions: null` with `source: null` when no confirmed row exists at all (both sources down, or never refreshed); `[]` when rows exist but none is computable. `dropped` counts rows skipped at read time because the source's data could not be used; a report older than the first stored bar is skipped and logged but never counted. **Correction made during commit 2:** an unvalidated *future* row never counts — an upcoming report is unvalidated by construction, and counting it would report a permanent `dropped: 1` on every healthy ticker. 2.4 passes this through, never 500.
12. **Refresh — one response shape, never null.** `earningsDates` is always `{"source": str|null, "stored": int, "dropped": int, "reason": str|null}`; `reason` is `null` on success, else `"rate_limited"` (primary rate limited, no fallback), `"down"` (both sources unusable), `"no_bars"` (empty bar store, no fallback attempted), `"error"` (anything else in the step). 2.4 handles one object, not object-or-null. The step runs after the bar upserts and before the frame cleanup (G8); any failure is logged at warning and the refresh still returns 200 — bars are the product. The cooldown is unchanged, so the extra calls are bounded by it. The scan pipeline does not fetch earnings dates (one `Ticker` call per winner; deferred).
13. **Alpha Vantage key in the query string — approved under two conditions (G14 otherwise forbids keys in URLs).** The API accepts the key only as `apikey=`; no header form exists. Conditions, both binding: (a) `logging.getLogger("httpx").setLevel(logging.WARNING)` in the client module, because httpx logs the full request URL at INFO; (b) typed errors never chain or format the original httpx exception (`HTTPStatusError.__str__` carries the URL) — `raise AlphaVantageError(...) from None`, message built from `function` + `symbol` only. Plus: the key is passed through `httpx` `params`, never formatted into a URL string; nothing logs `resp.url`; fixtures hold the body only; the recorder prints shape only. `test_alphavantage_client_sends_key_as_param_and_never_logs_url` triggers a real 4xx and a transport error and asserts through `caplog` that the key string appears in no record at any level. Limiter: process-wide `ratelimit.alphavantage_limiter`, 5 per rolling 60 s (the documented free per-minute cap); the daily cap is detected (`Information` body), not tracked.
14. **Date key so the writers collide on the PK.** `event_at` = midnight UTC of the Eastern calendar date (yfinance tz-aware index; Alpha Vantage `YYYY-MM-DD`), the same normalization `calendar_events` uses for Finnhub, so a Finnhub projection and a confirmation merge into one row (`meta` `||`). Bars pair by `ts.date()` (daily bars are stored at midnight of the trading date).
15. **`meta` written by this part** is exactly `meta.earnings = {source, validated, hour, epsEstimate, epsReported, surprisePct}` — one nested key, matching 2.1's convention that each writer owns its own. `meta.calendar` (2.1) is untouched by the `||` merge. A re-sync from the other source overwrites `meta.earnings` for that date (both sources agree on the date, so nothing is lost).
16. **Memory (G8).** Frames converted to rows, then `del` + `gc.collect()` inside the sync; only lists reach the DB layer; nothing frame-shaped in `app.state`.
17. **Ticker key.** `validate_ticker` on every entry point in this part; `.upper()` stays in `tickers.py` only.
18. **Two commits under this spec** (estimated ~700 lines, over the 600 threshold): `feat: earnings dates fetcher` (provider method, Alpha Vantage client + fetcher, validation, sync, refresh wiring, fixtures, recorder) then `feat: earnings reaction history` (`db.get_events`, the pure reactions function, the wrapper). Tests ride with their commit; the spec file is committed with the first.

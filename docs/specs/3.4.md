## Spec

Part 3.4 gives `compute_health` its first caller. A lifespan asyncio task, **off unless `SCHEDULER_ENABLED=true`**, runs one check at every 5-minute slot of the NYSE regular session (from `exchange_calendars` XNYS, holidays and early closes included) plus one settle check at 16:20 ET on every session day. Each check writes one `risk.health_checks` row and publishes `tf:risk:health` under Part 5's throttle: a regime change or a ≥ 10-point move since the last publish, at most one per 15 minutes, with CRITICAL bypassing the interval. `GET /market/health`, `GET /market/indicators` and `GET /market/history?days=` read Postgres only.

It must **not**:
- run the scheduler in the dev twin or in any test that does not switch it on explicitly
- queue a check behind the quotes lock, catch up missed slots, or run two checks at once
- make a request outside 3.2's cached, cooled-down, single-flight `get_core_quotes`; call FRED; or download from an endpoint
- let a Postgres failure delay or suppress a publish, or a Redis failure stop a row being written
- publish from the dev twin on the prod channel name (Redis pub/sub ignores the DB index)
- add a migration, write outside the `risk` schema, or change a 3.3 scoring rule
- build night mode, `POST /market/check`, the pre-market check or the weekend baseline (decisions 1 and 8)
- touch the prod container, the prod image tag or the prod database

Acceptance:
- every failure-branch row below has a passing test in `tf-risk-shield-dev`, and the 274 existing tests still pass
- the gating tests use frozen time against the real XNYS calendar (offline, bundled rules)
- the dev twin boots with the scheduler off; a one-off round trip writes one synthetic row to `tradingfirm_dev` and `:8013/market/*` serves it (decision 10)
- no live run; prod untouched; the deploy is the only thing on the G15 list

## Decisions the plan row leaves open

### 1. Scope: night mode splits out to 3.4b (**your call**)

The plan row's "every 30 min otherwise using futures (`ES=F NQ=F`) + VIX" can't be built from what is verified today:
- No 3.3 monitor reads futures, and ETF daily bars and `^VIX` don't move overnight. Running the 17-ticker check at night would give the same score ~34 times (~580 requests) for nothing.
- A futures overlay needs new provisional math **and** an unverified fact: how yfinance 1.5.1 dates an `ES=F` daily bar during the Globex evening session. The 3.2 canary only saw it during the day.
- 3.1 ran 2.6× over its estimate, 3.2 1.6× and 3.3 1.3×. With night mode in, 3.4's estimate crosses 700 lines of code.

**Recommendation:** 3.4 = market hours + settle, persistence, throttle, endpoints. **3.4b** = night mode: a live dating check first, then a `ES=F NQ=F ^VIX` download plus an overlay on the last settle score, gated by the `CMES` calendar (verified present in 4.13.2). The split gets a `docs/decisions.md` entry, because the plan is read-only.

**Alternative:** keep night mode here, with the live check as build step 0 and a stop before any overlay code.

### 2. Calendar: `exchange_calendars==4.13.2` (G4 done)

Probed in a throwaway `docker run --rm` of the dev image. Nothing was written to the repo, the twin or prod.
- `pip install --dry-run` adds only `korean_lunar_calendar 0.4.0`, `pyluach 2.3.0`, `toolz 1.1.0`. **pandas 2.3.0 and numpy 2.3.0 are unchanged.**
- XNYS: 2026-09-07 (Labor Day) and 11-26 are not sessions. 11-27 and 12-24 are sessions 09:30–13:00 ET, and `early_closes` for 2026 lists exactly those two. The calendar's `tz` is `America/New_York`.
- **Bounds:** the default calendar ends one year after it is built (`last_session 2027-09-10`).
- `CMES` exists (for 3.4b). It has no break modelled: the daily 17:00–18:00 ET halt reads as open.

**How it is used:** `market_calendar()` builds XNYS lazily, once per process. A date past its bounds rebuilds it once; if the date is still out of range, the check fails closed (no check, ERROR). The calendar is pure data with no network.

**Dependency change:** `requirements.txt` pin, so the twin is rebuilt with `--build`, which needs no ask. The prod image change waits for the go.

### 3. When a check runs

`scheduler.slot_for(now)` is a pure function of an aware UTC `now`. It returns `("market" | "settle", slot_start)` or `None`.
- **market:** the ET date is an XNYS session, `open ≤ now ≤ close`, and the slot is the ET minute floored to a multiple of 5. That gives 09:30 … 16:00 inclusive = **79 slots** (43 on an early-close day). §2's "~80" holds: 79 + 1 settle = 80 downloads, ~1,360 requests warm.
- **settle:** 16:20 ET on every session day, **early closes included**.
  - Why 16:20 and not close + 20: 3.3's partial rule treats a same-day bar as partial until 16:15 ET, and it is conservative on early-close days by design.
  - A single settle time always sees complete bars, and 3.3 stays unchanged.
  - Part 5's "end-of-day summary 4:15 PM" becomes this row.
- **Grace:** a slot runs only if `now − slot_start ≤ 60 s` (**new, provisional**). A later wake-up (tick overrun, laptop sleep, restart) skips the slot and logs `missed N slots` at WARNING. It never catches up.
- **Naive `now`:** `ValueError`.
- **Loop:** it sleeps until `next_slot_after(now)`, re-reads the clock, runs the slot if one is due, and repeats. Checks are awaited in sequence, so two never overlap.
  - 300 s ≥ 3.2's 255 s cold worst case (carry-forward).
  - A cold 255 s check makes the next slot late by up to 255 s, which the grace skips. A cold start happens once per container, so that is accepted.
- **Lock-held skip (carry-forward):** before computing, a check reads `quotes.download_in_flight()` (the per-loop lock's `.locked()`). If it is held, the check skips with a WARNING. Nothing in 3.4 can hold that lock during a check; the guard is for later callers.
- **One uvicorn worker, enforced and verified** (decision 8). Two workers would mean two schedulers and doubled downloads.

### 4. What a check does, in this order

1. **`compute_health(r, app.state.cooldowns, now=clock)`** — never raises for a source state (3.3).
2. **Trend.** `settleScore` / `settleCheckedAt` come from the latest **settle** row with a non-null score whose `checked_at` is before the XNYS session open of the check's ET date.
   - `score − settleScore ≥ +5` → `improving`, `≤ −5` → `declining`, otherwise `stable` (**±5 new, provisional**).
   - **The settle check itself:** its base is today's 09:30 open, so it compares against yesterday's settle. It never compares against its own row, and it runs before its own insert anyway.
   - **Yesterday's settle had a null score:** the query skips it and falls back to the latest *scored* settle before today's open, however old. `settleCheckedAt` shows how old.
   - No scored settle row at all, or a null current score → `trend: null`. The column allows NULL.
   - A read failure → WARNING, `trend: null`, and the check continues.
   - Why settle and not the previous tick: intraday, five of six monitors read yesterday's complete bars, so tick-to-tick deltas are almost always "stable". The comparison that means something is against yesterday's close.
3. **Throttle + publish** (decision 5). It runs before the insert, so a Postgres problem can never delay a CRITICAL.
4. **Insert** one row (decision 6). Null-score checks are recorded too (**your call**, decision 6).

- **Isolation:** each of steps 2–4 has its own `try`. A known dependency error is WARNING, anything else ERROR, and the next step still runs. An exception that escapes a check is caught by the loop (ERROR with type), and the loop goes on to the next slot. `CancelledError` always propagates.
- **`app.state.check_status`:** `{lastCheckAt, lastKind, lastScore, lastError}`, a small dict (G8), shown on `/health`.

### 5. Throttle (`scoring/alert_manager.py`)

`decide(last, health, now) -> (publish: bool, reason)` is pure. `last` = `{score, regime, publishedAt}` or `None`.

| condition, first match | publish | reason |
|---|---|---|
| `health.score is None` | no | — (no regime is not a regime change) |
| `last is None` | yes | `initial` |
| `regime == CRITICAL` and (`last.regime != CRITICAL` or `abs(score − last.score) ≥ 10`) | yes, **ignores the interval** | `critical` |
| ↳ **not symmetric:** *leaving* CRITICAL (`last.regime == CRITICAL`, `regime != CRITICAL`) gets no bypass; it falls through to the rows below and is held by the interval for up to 15 min like any other regime change | | |
| `now − last.publishedAt < 900 s` | no (held) | — |
| `regime != last.regime` | yes | `regime_change` |
| `abs(score − last.score) ≥ 10` | yes | `score_move` |
| otherwise | no | — |

- **Held, never lost:** the state only moves on a publish. A change held by the interval is compared against the same `last` next check, so it publishes once the 15 minutes pass if it still holds, and silently doesn't if it reverted.
- **CRITICAL (your call):** Part 5 says "bypass all throttling". Read literally, that means every 5-minute check while CRITICAL publishes (~79 a day). **Recommendation:** CRITICAL bypasses the interval, but still needs a trigger (entering CRITICAL, or a ≥ 10 move inside it). Hard-alert repetition belongs to the notifier (5.2), not here. **Alternative:** publish every CRITICAL check.
- **`recovery: true`** when `regime == HEALTHY` and `last.regime != HEALTHY`: Part 5's "crosses back above 70". It is a flag on a normal publish, not a bypass.
- **Stale health publishes normally,** with `stale: true` in the payload.
- **State key:** `tf:risk:state:health_published`, TTL 7 days, built by a new `cache.state_key(name)` (`name` through `canonical()`, lower-cased like `risk_key`'s kind). A wrong shape or unparseable JSON counts as absent → `initial`.
- **Channel:** `settings.health_channel`, default `tf:risk:health` (= `shared/constants.py`). The dev twin hard-codes `tf:risk:dev:health`. `cache.CHANNEL_HEALTH` moves to that setting (`config` can't import `cache`). There are no subscribers in the codebase today.
- **Payload** (JSON, `allow_nan=False`): `{score, regime, reason, recovery, previousScore, previousRegime, trend, stale, coverage, checkedAt, monitors: {name: score}}`.
  - `previousScore` / `previousRegime` are the last *published* values (Part 5: "from last alert"), `null` on `initial`.
  - This is the only place `previous*` appears. The trend base is `settle*` (decision 4).
- **Order and failure:** `PUBLISH` → then `SET` state.
  - `r is None` → no publish, WARNING.
  - A `PUBLISH` raise → WARNING, state untouched, retried next check.
  - A `SET` raise after a successful publish → WARNING, and the next check may publish again. Delivery is **at-least-once**, accepted.
- **Pub/sub is fire-and-forget.** A subscriber that was down reads `GET /market/health` on start (a Phase 6 note, recorded in decisions).

### 6. Persistence (`db.py`, no migration)

`risk.health_checks` exists since `001` in both `tradingfirm` and `tradingfirm_dev`. The CHECK constraints already allow NULL `score` / `regime` / `trend`.

**Insert:** `insert_health_check(pool, health, kind, trend, settle)`.
- `checked_at` = `health.checkedAt` (explicit, never `DEFAULT now()`); `score`, `regime`, `trend`.
- `indicators` = `$5::jsonb` of `{kind, coverage, stale, staleMonitors, monitors, inputs, settleScore, settleCheckedAt}`, serialized with `json.dumps(allow_nan=False)`. A `ValueError` there is a bug → ERROR, no row, publish already done.
- `kind` lives in the JSONB, not a new column, so no migration and no G15 migrate.

**Reads:** `latest_health_check(pool)`, `latest_scored_health_check(pool)`, `settle_base(pool, before)`, `health_history(pool, since)` (ascending, no `indicators` column). All run through the `checked_at DESC` index from 001.

**Null-score rows (your call):** **recorded** (recommended), so an outage shows in history as rows with `score: null` rather than a silent gap. **Alternative:** skip the insert.

**Write failure:** `(*DB_ERRORS, TimeoutError)` → WARNING, no row for that slot. `TimeoutError` is added because asyncpg's `command_timeout` raises it and it is deliberately not in `DB_ERRORS` (3.1). `db_pool is None` → WARNING, no row.

**Volume:** ~80 rows × ~4 KB of JSONB ≈ 320 KB/day, ~115 MB/year. No retention in 3.4.

### 7. Endpoints (camelCase, read-only, Postgres only)

- **Why Postgres only:** the current score and the history can't disagree, a failed insert shows up as an old `checkedAt`, and `cache.KIND_HEALTH` / `TTL_HEALTH` (unused) are deleted. No endpoint calls `compute_health` or a download.
- **`GET /market/health`** → the latest row:

  `{score, regime, trend, settleScore, settleCheckedAt, message, checkedAt, ageSeconds, kind, coverage, stale, lastScored}`
  - **`settleScore` is the trend base** (the latest scored settle before that check's session open), **not** the last published score. The endpoint serves no `previousScore`; the last publish lives only in the pub/sub payload.
  - `message` is Part 5's per-regime line, `null` for a null regime.
  - `lastScored` = `{score, regime, checkedAt}` of the latest scored row, present only when the latest row's score is null.
- **`GET /market/indicators`** → `{checkedAt, kind, coverage, inputs, monitors}` from the latest row. Each monitor is 3.3's contract + `weight`. A row whose JSONB has the wrong shape gives `monitors: null`, never a 500.
- **`GET /market/history?days=30`** → `{days, rows: [{checkedAt, score, regime, trend, kind, stale}]}`, ascending, null scores included.
  - `days` is an int, 1–90, default 30; out of range → 422.
  - An empty window → 200 with `rows: []`, not 404 (1.4's rule).
  - 90 days ≈ 7,200 rows ≈ 1 MB, accepted.
- **Errors for all three:**
  - no rows at all (health/indicators) → 404 with `{"detail": "no health checks yet"}`, so a fresh deploy before its first slot is distinguishable from a wrong route (FastAPI's `{"detail": "Not Found"}`)
  - `db_pool is None` or `(*DB_ERRORS, TimeoutError)` → 503, `{"detail": "database unavailable"}`
- **`/health`** adds `schedulerEnabled` and `lastCheckAt` (Part 5: "Service health + last check time"). `/` lists the three routes.

### 8. Lifespan, config, compose

- **`config.Settings`:** `scheduler_enabled: bool = False`, `health_channel: str = "tf:risk:health"`.
- **Lifespan:** it sets `app.state.cooldowns = MemoryCooldowns()` (carry-forward) and `app.state.check_status`. After Redis and Postgres, it starts `app.state.scheduler_task` only when the flag is on. It starts even with both dependencies down (then no cache, no publish, no rows, as in decisions 4–6).
- **Shutdown:** cancel the task and await it bounded by `wait_for(5 s)`, **before** the pool and Redis close.
  - Known limit: a check inside the yfinance thread can't be cancelled, so the thread outlives the task. On `docker stop` the process dies with it.
- **Compose:**
  - prod `risk-shield` gets `SCHEDULER_ENABLED: "true"`
  - `risk-shield-dev` hard-codes `SCHEDULER_ENABLED: "false"` and `HEALTH_CHANNEL: tf:risk:dev:health`
  - `docker-compose.dev.yml` (which replaces the prod container) inherits prod's values
- **Single worker, enforced.** uvicorn's `--workers` defaults to `$WEB_CONCURRENCY`, else 1, so an absent flag is not a guarantee.
  - **Where it's enforced:** both Dockerfile stages' `CMD` gain an explicit `--workers 1`. The prod `risk-shield` service has no `command:` override, so the prod stage's `CMD` is what runs.
  - **Test:** `test_dockerfile_pins_single_worker` reads `/app/Dockerfile` in the twin and asserts every `uvicorn` `CMD` carries `--workers 1`.

  - **Verified in the report:** the uvicorn process count inside `tf-risk-shield` after the deploy, read from `/proc/*/cmdline` because the slim image has no `ps`. Expected: exactly one.
- **yfinance tz cache (carry-forward, decided):** accept 17 extra requests per prod recreate. No named volume.

## Waiting for a go (G15)

One action, in this order.

**Before asking for the go** (the report shows each):
1. Every commit of the part is pushed, and `git rev-parse origin/main` equals `git rev-parse HEAD`.
2. The current prod image ID, recorded in the report: `docker inspect tf-risk-shield --format '{{.Image}}'`, plus the `tradingfirm-risk-shield:latest` ID.
3. The exact rollback, which is not git-revertable. Before rebuilding, tag the old image `docker tag <old-id> tradingfirm-risk-shield:rollback-3.3`. Rollback is then:
   - `docker tag tradingfirm-risk-shield:rollback-3.3 tradingfirm-risk-shield:latest && docker compose up -d --no-build risk-shield`
   - the old image predates `SCHEDULER_ENABLED`, so it ignores the variable
   - rows already written stay (no delete without its own go)

**On the go:**
4. `docker compose up -d --build risk-shield`: the 3.2 pins, `exchange_calendars`, `SCHEDULER_ENABLED=true`, `--workers 1`.
5. **Observe:**
   - the new image ID
   - `/health` (`schedulerEnabled: true`)
   - the uvicorn process count from `/proc` (exactly 1)
   - logs for the first check
   - one new row in `risk.health_checks`
   - `curl :8003/market/health`

   Outside market hours the first row waits for the next slot, so the go is best given before 16:20 ET on a session day. Until then `/market/health` answers 404 `no health checks yet`.

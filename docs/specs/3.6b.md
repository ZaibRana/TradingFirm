## Spec

Part 3.6b makes risk-shield generate macro briefs. A brief is generated at 07:30, 12:30 and 16:30 ET on XNYS sessions, when `run_check` publishes a `regime_change` or `critical`, and on `POST /macro/brief/generate`. Each generation:
- assembles 3.6a's inputs document
- calls ai-agent `POST /brief/macro` with it
- validates the response against a fixed contract
- stores one `risk.macro_briefs` row

`GET /macro/brief` serves the latest row. Everything that calls ai-agent runs only when `MACRO_BRIEF_ENABLED=true`, which stays false in prod and the twin.

It must **not**:
- build anything in ai-agent (4.6), call a real LLM, or add an Anthropic key anywhere
- turn `MACRO_BRIEF_ENABLED` on in any compose service, or give the twin a routable ai-agent URL
- retry ai-agent, back off or cool down after an ai-agent failure, truncate or repair a brief, or store a row without a valid response and `ready` inputs
- catch up missed slots, or generate on `initial` / `score_move`
- change 3.6a's document shape beyond `news.hours` (decision 4), or 3.4's throttle, payload or scoring beyond the one hook call (decision 5)
- subscribe to `tf:risk:health`, add a poller, write any Redis key, or publish a brief on pub/sub (Phase 5)
- touch prod except the G15 list

Acceptance:
- **Tests:** every failure-branch row names a passing test. In `tf-risk-shield-dev` the 562 existing tests still pass (measured on `65e6835`, the rebase base), except `test_inputs_news_request_within_route_bounds`, which is updated in place for decision 4.
- **Twin round trip (decision 8):** a row is generated with ai-agent mocked, served by `:8013/macro/brief`, then deleted. The twin's own `POST` answers 503 `macro brief disabled`.
- **Prod after the go:** `GET :8003/macro/brief` → 404, `POST` → 503, `/health` shows the brief fields. No row, no ai-agent call.

## Decisions

### 1. The ai-agent contract (fixed here; 4.6 implements it)

- **Request:** `POST {AI_AGENT_URL}/brief/macro`, JSON body `{"inputs": <assemble_inputs() result>}`. That is the stored document, never the endpoint's `cached` key.
- **Response 200:** one JSON object.

| field | rule |
|---|---|
| `regimeView` | string, non-blank, ≤ 1,000 chars |
| `keyRisks` | list of 1–8 non-blank strings, each ≤ 300 |
| `upcoming` | list of 0–10 non-blank strings, each ≤ 300 |
| `oneParagraph` | string, non-blank, ≤ 2,000 chars |
| `model` | optional string ≤ 100; blank or whitespace-only is returned as null, not rejected |
| any other key | rejected |
| the whole object | compact JSON ≤ 16,000 bytes, `allow_nan=False` (Python's `json` parses `NaN`, so the dump is the check) |

- **The byte measure:** The 16,000-byte bound is measured on compact JSON: `json.dumps(body, allow_nan=False, separators=(",", ":"))` with the default `ensure_ascii=True`, encoded as UTF-8, the same measure as `macro_inputs.encoded_size`. Every non-ASCII character counts as its JSON escape: 6 bytes, or 12 for an emoji.
- **camelCase over HTTP** (the API convention). This supersedes plan row 4.6's snake-case field names, recorded as its own `decisions.md` entry (decision 9, entry A), because the plan is read-only and 4.6 is written from `decisions.md`.
- **A violation is rejected, never truncated.** An LLM answer that breaks the contract is ai-agent's bug. A cut paragraph would store a brief that says less than it seems to.
- **One limits table, two copies:** `ai_agent_client.BRIEF_LIMITS` here, pinned by `test_brief_limits_pinned_to_spec`. 4.6 keeps a copy with its own pin test (the `NEWS_*` pattern).
- **The client** (`services/risk-shield/ai_agent_client.py`, `AiAgentClient`):
  - one `httpx.AsyncClient`, `follow_redirects=False`, no retries, no auth header (ai-agent has none; going-public list)
  - `BRIEF_TIMEOUT = 180` s hard (`asyncio.wait_for`), read at call time. Provisional: the answer is an LLM call with adaptive thinking, and 4.6 revisits it.
- **Outcomes** (typed errors, messages carry the status only):

| answer | error | log |
|---|---|---|
| 200, valid | none | INFO with the lengths |
| 200, violates the table / not JSON / not an object | `AiAgentBadResponse` | ERROR once per distinct problem, then DEBUG |
| 404 (today's scaffold has no route) | `AiAgentUnavailable` | **WARNING every time** "ai-agent has no /brief/macro (HTTP 404)" |
| 422 (our inputs contract drifted) | `AiAgentRejected` | ERROR |
| 429 (ai-agent's daily cap, 4.1), other 4xx, 5xx, 3xx | `AiAgentUnavailable` | WARNING with the status |
| transport error, timeout | `AiAgentUnavailable` | WARNING with the type |

- **No cooldown key and no backoff.** Calls are bounded by the cadence instead: 3 slots a day, regime briefs ≤ 1 per 30 min and CRITICAL ≤ 1 per 60 min (09:30–16:20 ET only until 3.4b), manual ≤ 1 per 10 min.

**Flag on before 4.6 ships** (someone sets `MACRO_BRIEF_ENABLED=true` while ai-agent is still the scaffold):
- **Each slot:** inputs are assembled, one request answers 404, and the loop logs **one WARNING**. No row. `lastBriefError = "ai-agent: HTTP 404 (no /brief/macro)"`.
- **Every slot calls again.** No cooldown, backoff or ERROR-once suppression hides the first real call once 4.6 lands, so the first slot after 4.6 generates a row.
- **Regime requests and manual calls do the same.** Their debounce and cooldown read *stored briefs*, so failures never block the next attempt. The manual route answers 502 each time.
- **Cost while it lasts:** one 404 per slot, per regime request and per manual call, plus the FRED reads the inputs already make (6 h cache).
- **Test:** `test_flag_on_ai_agent_404_warns_each_slot_no_backoff`.

### 2. One generation (`macro_brief.generate_once`)

`generate_once(state, client, *, trigger, clock) -> {outcome: generated|skipped|failed, cause, id, row}`, in order. `row` is the stored columns when generated: `POST /macro/brief/generate`'s 201 and `GET /macro/brief` build their body from a row through one serializer, so the two never drift (approved 2026-09-11).

1. **Busy:** `state.brief_lock` already held → skipped `busy`. It checks without waiting, so two generations never overlap or queue behind a 180 s call. `lastBriefError` unchanged.
2. **No pool** → skipped `database unavailable`, `lastBriefError = "database unavailable"`. Never spend an LLM call that can't be stored.
3. **Debounce** for `regime_change` / `critical` (decision 5) → skipped `debounced`. `lastBriefError` unchanged: a debounce is the design working.
4. **Inputs:** `macro_inputs.assemble_inputs(state, fred_client, inputs_http, now=clock())` directly. Never the endpoint's 60 s reuse.
5. **Not `ready`** (no checks, or no scored row, or the health read failed) → skipped `inputs not ready`, WARNING, **no LLM call**, `lastBriefError = "inputs not ready"`.
6. **Call:** `client.brief(inputs)` → a validated response, or a typed error → failed. `lastBriefError = "ai-agent: <cause>"`, e.g. `ai-agent: HTTP 404 (no /brief/macro)`, `ai-agent: AiAgentBadResponse (keyRisks: 9 items)`.
7. **Insert:**
   - `generated_at` = `clock()` after the response
   - `regime` / `health_score` from `inputs.health`: its score and regime, or `lastScored` when the score is null
   - `brief_text` = `oneParagraph`, `brief` = the validated response, `inputs` = the document
   - the `trigger`
   - A `DB_FAILURES` raise → failed, `lastBriefError = "insert: <type>"`, WARNING "brief lost".
8. **`app.state.brief_status`** = `{lastAttemptAt, lastBriefAt, lastBriefId, lastTrigger, lastError}`. `/health` shows `lastError` as `lastBriefError`. A success clears it. The document is never kept in state (G8).

- **Isolation:** a raise from a bug is caught by the loop (ERROR) and by the endpoint (500). `CancelledError` propagates, and nothing is stored mid-call.
- **New `db.py` helpers** (the `risk` schema only):
  - `insert_macro_brief(pool, *, generated_at, regime, health_score, brief_text, brief, inputs, trigger) -> uuid`: `json.dumps(allow_nan=False)` for both JSONB
  - `latest_macro_brief(pool)`
  - `last_brief_at(pool, trigger=None)`: `max(generated_at)`, optionally for one trigger
  - `slot_brief_exists(pool, window_start, window_end)`: decision 3

### 3. Slots, holidays included (open item 1 closed)

- **When:** `SLOT_TIMES_ET = (07:30, 12:30, 16:30)` on an ET date `d` exactly when `scheduler.session_bounds(d)` is not None, using the same cached XNYS calendar as the health checks.
  - Weekends and XNYS holidays (Thanksgiving, Christmas) have no slots.
  - Early-close days keep all three: 12:30 is before the 13:00 close, and 16:30 is after the 16:20 settle.
  - 16:30 follows the 16:20 settle, so it reads that day's settle row.
  - 07:30 reads the previous settle, fresh by 3.6a's rule, with `healthAgeMinutes` showing ~900.
- **The loop** (`macro_brief.run_brief_loop(state, client, *, clock, wait)`) follows 3.5's pattern, on the 3.4 follow-up's harness:
  - It waits for the next slot, or a queued regime request (decision 5), whichever comes first.
  - **The wait (v2 item 7):** repeated chunks of `wait(wallclock.wait_seconds(target, clock()))`, re-reading the clock after each. The default `wait` is `asyncio.wait_for(queue.get(), timeout)`, answering the queued reason or None on timeout; tests inject a fake that moves `LoopClock`. No chunk is longer than 60 s.
  - **Why:** a single wait to the next slot runs on the Docker VM's monotonic clock, which stops while the Mac sleeps (decisions 2026-09-11). `asyncio.wait_for` uses the same clock.
  - **Early wake:** nothing.
  - **On a slot:**
    - late by more than `BRIEF_GRACE_SECONDS = 1800` (provisional) → WARNING "skipped, not caught up"
    - the slot already has a brief (below) → skipped, INFO, no LLM call
    - otherwise `generate_once(trigger="slot")`
  - **Why 30 min of grace:** a laptop that wakes at 08:00 still gets a morning brief. Past that, the next slot is the better brief.
  - **A raise** → ERROR, and the loop goes on. Cancellation propagates.
  - **`next_brief_slot_after(now)`** searches 15 days (the scheduler's horizon). None → ERROR, then a 300 s wait through the harness (≤ 60 s chunks).

**"This slot already has a brief":**
- **The rule:** a row with `trigger = 'slot'` and `slot_start ≤ generated_at < slot_start + BRIEF_GRACE_SECONDS + BRIEF_TIMEOUT` (1,800 + 180 = 1,980 s). `db.slot_brief_exists(pool, slot_start, slot_start + 1980 s)` checks it.
- **Why that window:** a slot generation can only start inside the grace window and must finish within the timeout, so every row this slot can produce lands in it. The gap to the next slot is 5 h (4 h for 12:30 → 16:30), so two slots never share a window.
- **What doesn't count:**
  - a `manual` or `regime_change` brief in the window: a manual brief at 07:20 doesn't stand in for the 07:30 slot
  - a `slot` row from another slot (the previous day's 16:30)
- **The read fails** (`DB_FAILURES`) → the check answers "exists: unknown", and `generate_once`'s no-pool / insert paths then decide. It never generates twice on a guess: a failed read skips with `lastBriefError = "database unavailable"`.
- **Restart at 07:45 (explicit test):** the 07:30 slot's brief was stored at 07:31:10. The container restarts, and the loop wakes at 07:45 (15 min late, inside grace). The check finds the row, so it skips with zero ai-agent calls. The next generation is 12:30. Test: `test_brief_loop_restart_at_0745_skips_generated_slot`.

### 4. Monday 07:30's news window: **option A (decided)**

- **The problem:** 3.6a asks for `hours=24`. Monday's 07:30 brief sees Sunday 07:30 onward, and misses Friday 16:00 → Sunday 07:30.
- **The fix:**
  - `news_hours(now) = clamp(ceil(hours since the latest XNYS close before now's ET date), 24, 96)`
  - Every assembly uses it, the inputs endpoint included, so the stored `news.hours` says which window was used.
  - `limit` stays 50: a weekend's news competes, and the newest 50 still win. The input size stays bounded.

| now (ET) | previous close | hours |
|---|---|---|
| Tue 2026-09-15 07:30 | Mon 09-14 16:00 | 15.5 → **24** |
| Fri 2026-09-11 16:30 | Thu 09-10 16:00 | 24.5 → **25** |
| Mon 2026-09-14 07:30 | Fri 09-11 16:00 | 63.5 → **64** |
| Tue 2026-09-08 07:30 (after Labor Day) | Fri 09-04 16:00 | 87.5 → **88** |
| Fri 2026-11-27 07:30 (after Thanksgiving) | Wed 11-25 16:00 | 39.5 → **40** |
| Mon 2026-12-28 07:30 (Christmas Fri) | Thu 12-24 13:00 (early close) | 90.5 → **91** |
| Mon 2026-12-28 16:30 (the same day's 16:30 slot) | Thu 12-24 13:00 (early close) | 99.5 → **96** (the ceiling; added 2026-09-11) |

- **Constants, side by side in `macro_inputs.py`** so the pair stays visible: `NEWS_HOURS_MIN = 24` and `NEWS_HOURS_MAX = 96`, directly beside the pinned copy `DATA_ENGINE_NEWS_MAX_HOURS = 168` / `DATA_ENGINE_NEWS_MAX_LIMIT = 100`.
- **The one 3.6a test is updated in place, not joined by a parallel one.** `test_inputs_news_request_within_route_bounds` becomes parametrized over the seven rows (the seventh pins the 96 h ceiling by a request, not only a constant). For each it asserts:
  - the request's `hours` = the table value, and `limit=50`
  - `(NEWS_HOURS_MIN, NEWS_HOURS_MAX, DATA_ENGINE_NEWS_MAX_HOURS, DATA_ENGINE_NEWS_MAX_LIMIT) == (24, 96, 168, 100)`
  - `NEWS_HOURS_MAX ≤ DATA_ENGINE_NEWS_MAX_HOURS`, with a message naming data-engine's pin test
- **Other code:** `scheduler.previous_close_before(day)` is a new pure helper, and `news_section(http, hours)` takes the window.

### 5. The regime-change trigger

- **The hook** is the one change to 3.4 code. In `scheduler.run_check`, after the publish step: if `published["published"]` and `published["reason"] in (REASON_REGIME_CHANGE, REASON_CRITICAL)`, call `macro_brief.request_brief(state, reason)`.
  - It never awaits, never raises (wrapped, ERROR on a bug), and never delays the insert.
- **`request_brief`:**
  - `state.brief_queue` is None (flag off) → nothing
  - otherwise `put_nowait(reason)`; `QueueFull` → INFO "brief request dropped, one already queued"
  - The queue is `asyncio.Queue(maxsize=1)`, created in the lifespan only when the flag is on.
- **It inherits 3.4's throttle:** 15-min interval, CRITICAL bypass, and leaving CRITICAL is held.
  - Publish is at-least-once, so a repeated publish can enqueue twice; the debounce absorbs it.
  - `initial` (after a restart) and `score_move` never trigger.
- **Debounce in `generate_once`, read from Postgres** (it survives a restart, and nothing goes in Redis):
  - `regime_change`: skip if any brief has `generated_at > now − 30 min`. That covers "a scheduled brief ran in the last 30 min".
  - `critical`: skip if a `critical` brief has `generated_at > now − 60 min`. The 30-min rule doesn't apply.
  - `slot` and `manual` aren't debounced; manual has its own cooldown (decision 6).
  - It counts stored briefs only, so an ai-agent failure never debounces the next request (decision 1).
- **Until 3.4b** a regime brief can fire only 09:30–16:20 ET.

### 6. Endpoints

- **`GET /macro/brief?includeInputs=false`:** the latest row, Postgres only, whatever the flag.
  - **Body:** `{id, generatedAt, ageMinutes, trigger, regime, healthScore, briefText, brief, freshness}`. `freshness` is `inputs.freshness`; `inputs` is added only with `includeInputs=true`.
  - No row → 404 `no macro brief yet`. No pool or `DB_FAILURES` → 503 `database unavailable`.
- **`POST /macro/brief/generate`** (trigger `manual`), checked in this order:

| state | answer |
|---|---|
| flag off | 503 `macro brief disabled` |
| no pool | 503 `database unavailable` |
| `brief_lock` held | 409 `generation in progress` |
| last *stored* brief of any trigger < 600 s ago | 429 with `Retry-After` |
| generated | 201, the same body as `GET` |
| **skipped, inputs not ready** | **422 `{"detail": "inputs not ready"}`**, no LLM call, `lastBriefError` set |
| ai-agent failure | 502 `ai-agent: <cause>` |
| insert failure | 503 `brief lost: database unavailable` |

- **409 means "try again shortly" and 429 means "too soon".** 422 means the request can't succeed until a scored health check exists. It stays separate so a caller doesn't retry it on a timer.
- It blocks for up to 180 s. No auth: carried to going public.
- **`/health`** adds `lastBriefAt`, `lastBriefTrigger`, `lastBriefError`. **`/`** lists both routes.

### 7. Lifespan, config, compose

- **Flag on:** `brief_queue`, one `AiAgentClient` (at `settings.ai_agent_url`), and the brief task joins the shutdown `running` dict as "Macro brief". The client closes after the tasks, before the pool and Redis.
- **Flag off:** no queue, client or task. `brief_status` and `brief_lock` always exist (small; `/health` and the endpoint read them).
- **Settings:** none new (3.6a added both). `BRIEF_TIMEOUT` and `BRIEF_GRACE_SECONDS` are module constants.
- **Compose:** unchanged. Prod has `MACRO_BRIEF_ENABLED: "false"`; the twin hard-codes false + `.invalid`. Turning prod on is a G15 item after 4.6 ships, not this part.
- **Shutdown during an LLM call:** cancelled, nothing stored, bounded by `SCHEDULER_SHUTDOWN_TIMEOUT`.

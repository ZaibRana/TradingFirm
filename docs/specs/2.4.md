# Spec — Part 2.4: Dossier endpoint

Status: **draft v2, awaiting approval** (v1 reviewed in chat; the six edits are folded in below). Nothing outside this file is written until "approved" for 2.4 appears in chat (G1). Built as three commits under this one spec (decision 20).

## Spec

`GET /dossier/{ticker}?horizon=swing` returns one camelCase JSON document that assembles, for a single ticker, the indicator snapshot and zones (Part 1.7, from stored bars), news, events, recommendations and profile (Part 2.1, Finnhub), filings (Part 2.2, EDGAR) and earnings reaction history (Part 2.3, stored events + bars), each as an object carrying its own `status` ∈ `ok` / `truncated` / `error` / `unconfigured`, size-capped at 30 headlines and 10 filings, cached in Redis 15 min in market hours and 60 min outside, refreshing stale bars first. It must never 500 or 502 because an upstream source failed — a failing source is a section status and the rest of the document still returns 200 — never turn a database failure into a section status (a DB read that raises is a 503), never exceed the stated per-source timeout or per-dossier call budget, never keep calling a source the SEC or Finnhub has just refused (cooldown), never serve a dossier assembled from an error section for longer than 2 minutes, and never call an external API from a test. Acceptance: every failure-branch row below has a passing test, the eleven named tests exist under those names, `docker exec tf-data-engine-dev pytest tests/test_dossier.py -v` is green with `respx` refusing any unmocked host, and prod is untouched until the G15 go.

## Decisions the plan row leaves open (as proposed)

**Shape**

1. **Every section is an object with a `status`, never a bare list.** The four values are `ok`, `truncated`, `error`, `unconfigured`. An `error` section carries `{status: "error", reason, detail}` with `reason` ∈ `timeout` / `rate_limited` / `blocked` / `auth` / `cooldown` / `upstream` and `detail` a short message (never a URL, never a key — G14, spec 2.3 decision 13), **plus the same empty payload key its `ok` form has** (`items: []`, `rows: []`, `reactions: null`), so a consumer never branches on a missing key. There is no `db` reason: a database failure is a 503, not a section (decision 7). `unconfigured` is the source's key/User-Agent being empty (`FinnhubNotConfigured`, `EdgarNotConfigured`) — the dev twin's normal state, and a different fact from `error`.
2. **Sections and their `ok` payloads.** `bars {status, interval, lastBarDate, staleWeekdays, refreshed}`; `indicators {status, ...the 1.7 snapshot..., zones, benchmarks}`; `news {status, items, count, truncated}`; `events {status, items}`; `recommendations {status, items}`; `filings {status, rows, truncated}`; `earnings {status, reactions, dataQuality}`; `profile {status, ...profile fields}`. Top level: `ticker`, `horizon`, `asOf`, `generatedAt`, `cached`, `sections` (the eight above), `budget {upstreamCalls, elapsedMs, bySource}` — see decision 12.
3. **`truncated` is one flag with one meaning: "this list is not the complete window."** `status: "truncated"` ⟺ the section's `truncated` boolean is true. For news it means the 30-headline cap applied; for filings it means the 10-filing cap applied **or** 2.2's block flag was true (EDGAR's `recent` block did not reach back `days`). Both causes read the same downstream — the list is incomplete — and the log line names which. No second flag.
4. **Earnings passes 2.3 through untouched.** `dataQuality` is the exact `{source, dropped, disagreements}` object 2.3 returns, and `reactions: null` (no confirmed report exists) stays distinct from `[]` (reports exist, no bars explain them). 2.4 computes no averages and re-counts nothing.
5. **Caps are applied after sorting, never before.** News: newest first, keep 30. Filings: newest `filed_on` first, keep 10. Events: the ±120-day window `get_events` is asked for, no cap. Recommendations: the last 4 months Finnhub returns, no cap.
6. **NaN → null.** One `nan_to_none` field validator applied to every float field in `dossier/models.py`; `float('nan')`/`inf` serialize as JSON `null`, not `NaN`. camelCase via `Field(alias=...)` + `by_alias`, the `scanners/models.py` convention.

**Degrade on upstream, 503 on the database**

7. **One error boundary per section, and the database is outside it.** Each section builder is wrapped by `_section(name, coro)`, which catches `FinnhubError`, `EdgarError`, `asyncio.TimeoutError`, `ValueError` and bare `Exception`, maps it to a `reason`, logs at warning with the ticker and the exception type, and returns the `error` object. It **re-raises** the database exception tuple `db.DB_ERRORS = (asyncpg.PostgresError, asyncpg.InterfaceError, OSError)` — named once in `db.py` so tests raise the same thing the code catches — before any of that mapping. Sections run under `gather(..., return_exceptions=True)`; the assembler scans the results, and if any is a `DB_ERRORS` instance it raises `HTTPException(503)` for the whole dossier. A DB failure is never a degraded section: the dossier is a document about stored data, and half of it silently missing is worse than an error. `HTTPException` is never raised inside a section builder. **No 502 anywhere in the dossier path** — the 502s in `/stocks/{ticker}` and `/stock/{ticker}/refresh` are unchanged, but the dossier calls the refresh helper, not the endpoint, and reads its failure as `bars.status`.
8. **The four status codes the endpoint itself may return.** `400`: `validate_ticker` raises, or `horizon` is not `swing`. `404`: no stored daily bars **and** the refresh did not produce any. `503`: `app.state.db_pool` is None, or any DB read raises — wherever it happens. `200`: everything else, including every upstream failure.
   **Which DB reads happen where.** *Before the fan-out, sequentially:* the daily-bar read that decides 404 and staleness, and (on a stale ticker) the refresh helper's own writes and re-read. A 503 from these costs no upstream call. *Inside the fan-out:* `indicators` (bars + SPY + sector ETF + `get_stock`), `events` (`upsert_events` then `get_events`), `earnings` (`get_events` + `get_bars`), `news` (`upsert_news`). A 503 from these arrives after the fan-out has already spent its calls — accepted: correctness over a wasted call budget.
9. **Stale bars, concretely (weekday rule; holidays deferred to Phase 3's `exchange_calendars` dependency — hence `staleWeekdays`, not `staleTradingDays`, until that name is true).** The *reference session* is today's ET date if it is a weekday and the ET clock is ≥ 16:00, else the most recent earlier weekday. Bars are stale when the number of weekdays in `(lastBarDate, referenceSession]` is **> 1**. Stale → call the refresh helper once (subject to the existing 15-min per-ticker refresh cooldown). Four outcomes:

    | outcome | `bars.status` | `refreshed` |
    |---|---|---|
    | not stale, no refresh call | `ok` | `false` |
    | refreshed and the newest bar advanced past the threshold | `ok` | `true` |
    | refresh ran, succeeded, newest bar unchanged (holiday week, lagging provider) | `stale` | `true` |
    | refresh raised, timed out, or the ticker was on refresh cooldown | `stale` | `false` |

    The third row is "we asked, the source had nothing newer" — a normal state, not an error, and it takes the normal TTL (decision 10). Cost is bounded twice over: the 15-min per-ticker refresh cooldown, and the dossier's own cache window, so at most one refresh attempt per cache window. Indicators are always computed from whatever bars the store holds after this step.
10. **A `stale` bars section does not make the dossier an error dossier** for TTL purposes (decision 11): stale is a normal weekend/holiday state, and only `status: "error"` shortens the TTL.

**Cache**

11. **Key `tf:cache:dossier:{horizon}:{ticker}`** through `cache.dossier_key(ticker, horizon)` — ticker via `validate_ticker`, horizon from the validated enum, so both are already canonical (G1.5: one normalization function). TTL: **900 s** when `get_market_status()` is `market_open`, **3600 s** otherwise, and **120 s** when any section's status is `error`. `cached` is set on the way out and excluded from the stored body (the 1.7 convention). Redis rules are 1.7's, one test each: Redis absent → compute, no cache; GET raises → warn, compute; SET raises → warn, still return; corrupt/mis-shaped body → warn, recompute, overwrite.

**Budget**

12. **Per-source timeout 8 s** (`asyncio.wait_for` around each section, covering limiter wait + HTTP; the clients' own 10 s HTTP timeout stays as the inner bound). Over it → `status: "error"`, `reason: "timeout"`. Sections run concurrently under one `gather`, so **the fan-out cannot exceed ~8 s**: the 25 s outer `wait_for` is a defensive guard against a builder that never yields, not a reachable budget — `test_total_budget_caps_fanout` patches the outer constant *below* the inner one to exercise it. **Refresh step budget 20 s**, sequentially before the fan-out (accepted: the fan-out's indicator section must read the bars the refresh wrote). Worst case ≈ **28 s** (20 + 8), typical warm dossier < 1 s (DB + Redis only). `budget.elapsedMs`, `budget.upstreamCalls` and `budget.bySource` are reported in the response, read from each client's `calls_made` delta.
13. **Upstream calls per uncached dossier — the number to argue with.** Five Finnhub calls stand.

    | source | cold (nothing cached) | warm 24 h keys, cold 15 min keys | fully cached |
    |---|---|---|---|
    | Finnhub | **5** — news, earnings calendar, surprises, recommendations, profile | 1 (news) | 0 |
    | EDGAR | **2** — CIK map, submissions | 1 (submissions) | 0 |
    | yfinance | 0, or **2** downloads if bars are stale | same | same |
    | yfinance `Ticker` / Alpha Vantage | 0, or ≤ 1 + ≤ 1 inside the refresh's earnings step | same | same |
    | **total** | **7**, or **11** with a stale-bar refresh | **2** | **0** |

    This matches plan §5's budget line ("~5 Finnhub + 2 EDGAR ≈ 10 per ticker, cached 15 min"). Against Finnhub's 60/min limiter, 5 calls per cold dossier bounds the scanner at **12 cold dossiers per minute**; after the first day-cycle the 24 h keys leave 1 call each, i.e. **60 warm dossiers per minute**. The binding constraint is not Finnhub: it is Alpha Vantage's **25 calls/day**, reached only through refreshes of tickers whose earnings dates yfinance cannot supply. These four numbers (7 / 2 / 0 / 11) are the oracle for `test_budget_counts_upstream_calls`, asserted against the `respx` call log.
14. **Each section owns its calls and its write; `sync_context` is not on the dossier path.** `sync_context` fetches all three bodies and writes only after all three succeed, so one failing fetch would drop the news rows too, and there is no `db.get_news` to read them back from — "only `news` is `error`" is unreachable through it. Instead: **news** = `company_news` → `news_records` → `upsert_news`, and the section is built from the raw body it already holds; **events** = `earnings_calendar` + `earnings_surprises` → `calendar_events` + `surprise_events` → `upsert_events` → `db.get_events(pool, ticker, since=-120d, until=+120d)`. Reading events back from the store rather than reshaping the raw bodies is what makes the section include 2.3's `meta.earnings` rows and any Finnhub projection merged into the same PK. If the calendar or surprises call fails, the `get_events` read still runs: `events` is `ok` from the store and only that fetch is lost. `sync_context` stays exactly as 2.1 built it, as the ingest entry point, untouched by this part.
15. **Filings: `recent_filings(forms=('8-K','4'), days=30)`**, no store-back on the dossier path (2.2's `sync_filings` stays refresh/ingest work) — filings are read-only here.
16. **Cooldowns, in `cache.py`.** `EdgarRateLimited` (403 **or** 429 — 2.2 maps both) sets `tf:cache:cooldown:edgar` for **900 s**: a 403 means blocked, and CLAUDE.md says stop. `FinnhubRateLimited` (429) sets `tf:cache:cooldown:finnhub` for **60 s**, the width of the per-minute window. A set cooldown makes that source's sections `{status: "error", reason: "cooldown"}` **before any HTTP**. Cooldowns are source-wide, not per-ticker: the refusal is about us, not the ticker. Redis absent or raising → the in-memory fallback, fail-open.
    **Alpha Vantage is not a section, so its cooldown acts one level down.** `AlphaVantageCapped` (the 25/day cap) and `AlphaVantageRateLimited` set `tf:cache:cooldown:alphavantage` for **3600 s**, and `sync_earnings_dates` (2.3) checks that key immediately before its fallback call and skips it. That surfaces in the refresh response as `earningsDates.reason: "cooldown"` — **one new value in 2.3's existing enum** (`null` / `rate_limited` / `down` / `no_bars` / `error` / `cooldown`); the shape, the refresh's 200, and every other 2.3 behaviour are unchanged. The dossier sees this only through the refresh helper, never as a section.
17. **The `refactor:` commit that comes first — behaviour-preserving.** Three moves, no behaviour change: (a) the per-ticker refresh cooldown logic in `main.py` (`InMemoryStore.get_refresh_cooldown` / `set_refresh_time` and the Redis-or-memory branch inside `refresh_stock`) becomes one generic pair in `cache.py`, `cooldown_remaining(redis, memory, name)` / `start_cooldown(redis, memory, name, ttl)`, with the in-memory dict moving to a small `MemoryCooldowns` class that `InMemoryStore` holds; (b) the body of `get_indicators` is extracted into `dossier/sections.py::indicators_section()` so the endpoint and the dossier share one bars → snapshot → cache path instead of two copies; (c) `cache.cached_json()` gains an optional `ttl_for: Callable[[Any], int]` — today's `ttl` is fixed before `fetch()` runs, and the dossier's TTL (900/3600 vs 120) is not known until the body exists. Precedent `dc739ed`. Proof of "behaviour-preserving": the existing 1.2 and 1.7 test files pass **unchanged**, the report shows the collected test count before and after, and the only new test in this commit is `test_cooldown_helpers_redis_and_memory`.
18. **`horizon` is not decorative.** It is a `str Enum` with the single member `swing`; anything else is 400 (FastAPI would give 422 for a bare enum parameter, so it is a plain `str` validated in the handler — the requirement says 400). It selects a row of `HORIZON_PROFILES` in `dossier/__init__.py`: `swing = {news_days: 7, filing_days: 30, filing_forms: ('8-K','4'), reactions: 8, events_window_days: 120, bars_interval: '1d'}`. Every window in the assembly reads from that row, and the cache key carries the horizon, so adding `intraday` in Phase 6 is a second row and no branching.
19. **Memory (G8).** The indicator path already `del`s its frames and calls `gc.collect()`; the dossier adds no DataFrame of its own and stores nothing frame-shaped in `app.state`. `FinnhubClient` and `EdgarClient` are created once in `lifespan` — they are not currently created at all — alongside `av_client`, and closed on shutdown.
20. **Three commits under this spec** (estimate ~1,050 lines, over the 600 threshold): `refactor: cooldown keys, indicator body and cached_json TTL move out of main` (decision 17) → `feat: dossier assembly` (`dossier/` package: models, sections, assembler, caps, budget; tests without a route) → `feat: dossier endpoint` (route, horizon validation, staleness + refresh, Redis TTL policy, TestClient shape tests). Tests ride with their commit; this spec file is committed with the first.

## Writes

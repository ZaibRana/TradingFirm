## Spec

## Decisions the plan row leaves open

### 1. Who polls Finnhub: **A, as the plan says (decided)**

- **The split:** risk-shield polls, and data-engine stores the items through `POST /news/ingest`.
- **Why A:**
  - data-engine stays a passive store with no background task.
  - risk-shield already has the loop, the cooldown machinery and the `--workers 1` pin.
  - 3.6, the first reader, lives in risk-shield.
- **The cost:** the Finnhub key lives in two processes, each with its own limiter.
  - data-engine's limiter (60 per 60 s with a 1.2 s gap) caps it at 50 calls a minute.
  - risk-shield adds one call per 15 minutes, so the worst combined minute is 51, under the free tier's 60.
  - Cooldowns are handled in decision 4.

### 2. Cadence: every 15 min, around the clock (**decided**)

- **Slots** are wall-clock quarter hours (:00, :15, :30, :45 UTC), and the poll is not gated by XNYS.
  - News breaks overnight and at weekends, and 3.6's 07:30 ET brief reads the last 24 hours.
  - That is 96 Finnhub calls a day.
- **A late wake-up** (laptop sleep, restart) runs one poll right away, then returns to the slots. The page's span covers the gap (~41 h on 2026-09-10), and the overlap warning (decision 3) says when it didn't. It never catches up with more than one poll.
- **Own flag and own task.** `NEWS_POLL_ENABLED` (default false) is separate from `SCHEDULER_ENABLED`, so either one can be switched off alone. Prod compose sets it to true, and the twin hard-codes false.

### 3. No incremental fetch: the whole page, deduped (corrected after the live check)

- **Every poll sends the whole page.** On 2026-09-10 Finnhub's general page was 100 items spanning ~41 h, so polls 15 minutes apart overlap almost entirely. Ingest's `ON CONFLICT (ticker, url) DO NOTHING` drops what is already stored: ~100 rows sent per slot, nearly all ignored.
- **No `minId` and no news state in Redis.**
  - **Why:** the live check found ids in Finnhub's pickup order, not publish order. Whether Finnhub applies `minId` before or after choosing its newest 100 can't be verified, and dedup needs neither.
  - Redis is read in the poll path only for the two cooldowns (decision 4).
- **Overlap warning** (replaces v2's "page full"):
  - **When:** the page's oldest `datetime` is newer than the previous successful poll's time (`news_status.lastSuccessAt`).
  - **What it says:** WARNING "news page does not reach back to the previous successful poll, items may have been missed". The ingest still runs.
  - **Not on the first poll after start,** since there is no previous success.
- **`news_status` gains `pageSpanMinutes` and `oldestAt`.** They are set whenever Finnhub answers a non-empty page and are shown on `/health`, so a shrinking page is visible before the overlap warning fires.
- **A late wake-up** (decision 2) is covered by the same overlap: a gap shorter than the page span loses nothing, and a longer one fires the warning.

### 4. Finnhub in risk-shield (`monitors/finnhub_client.py`)

- **Pattern:** it copies data-engine's client pattern, not its code (3.1).
  - The key goes in the `X-Finnhub-Token` header, never the URL, so no G14 exception is needed.
  - `settings.finnhub_api_key` is a `SecretStr`.
- **Limits:**
  - its own `ratelimit.finnhub_limiter`: 60 per 60 s plus a 1.2 s gap
  - an 8 s hard timeout (`wait_for`), like FRED's
- **Typed errors** live in `monitors/errors.py`: `FinnhubNotConfigured` (raised before any HTTP), `FinnhubRateLimited` (429), `FinnhubNotAuthorized` (401/403), and `FinnhubError` for anything else, including a body that is not a list. Messages carry the status only, raised `from None`.
- **risk-shield's own cooldown** reuses 3.2's machinery with `SOURCE_FINNHUB` (`tf:risk:cooldown:FINNHUB`):
  - 429 → 900 s
  - 401/403 → 3600 s
  - with no Redis, the memory clock remembers either for 900 s, as FRED's does

**data-engine's cooldown is read too (correction 4).** A 429 is account-level, so a poll skips while either cooldown runs.
- **The key:** data-engine sets `tf:cache:finnhub` for 60 s after a dossier 429 (`dossier/assemble.py:216`, `cache.SOURCE_FINNHUB` / `TTL_COOLDOWN_FINNHUB`). Prod risk-shield and prod data-engine both use Redis DB 0; both twins use DB 1, so each twin reads its own twin's key.
- **Read-only:** one `TTL` per poll. risk-shield never writes it.
- **Fail-open:** an absent key, a raising `TTL` or no Redis reads as clear. A key rename in data-engine would fail open silently, so the name is pinned on both sides:
  - risk-shield: `DATA_ENGINE_FINNHUB_COOLDOWN_KEY = "tf:cache:finnhub"`, asserted by `test_poll_once_skips_while_data_engine_finnhub_cooldown`
  - data-engine: `test_finnhub_cooldown_key_is_pinned_for_risk_shield`, a new test in `test_cooldowns.py`, whose message names risk-shield as the reader
- **Why read rather than accept separate cooldowns:** it costs one Redis read per 15 minutes. A poll that lands inside data-engine's refused minute is the only thing the read prevents, and G6 ranks that above the coupling.
- **Not symmetric:** data-engine does not read risk-shield's key. That would be a data-engine change outside this part (carried forward).

### 5. `POST /news/ingest` (data-engine) and the one limits table

**The limits, stated once.** Both sides implement this table:
- data-engine's route model rejects a violation with a 422.
- risk-shield's converter makes a violation impossible before it sends.
- The two services share no Python package (`shared/` is in neither build context), so each keeps a copy of the numbers, commented `spec 3.5 decision 5`.
- Each copy has a pin test: `test_ingest_limits_pinned_to_spec` (data-engine) and `test_converter_limits_pinned_to_spec` (risk-shield). Changing one side without the other fails a test.

| field | limit | route (422 on violation) | converter (before send) |
|---|---|---|---|
| items per request | 1–200 | 422 | chunks of ≤ 200; no POST when empty |
| `url` | `http://` or `https://`, ≤ 2,048 chars, no NUL | 422 | NUL stripped; wrong scheme or > 2,048 → **dropped**, counted |
| `title` | non-blank after strip, ≤ 1,000 chars, no NUL | 422 | NUL stripped, then whitespace; blank → dropped; > 1,000 → **truncated**, counted |
| `summary` | ≤ 10,000 chars, no NUL | 422 | NUL stripped; missing → `""`; > 10,000 → **truncated** |
| `source` | ≤ 100 chars, no NUL | 422 | NUL stripped; missing → `""`; > 100 → **truncated** |
| `publishedAt` | timezone-aware ISO 8601 | 422 | built in UTC from `datetime`; not an int, ≤ 0 or out of range → dropped |
| extra fields (`ticker`, …) | none allowed (`extra="forbid"`) | 422 | never produced |

- **Why NUL is in the table:** Postgres `TEXT` rejects `\x00`. Without the rule, a NUL would reach asyncpg as a `DataError` (a `PostgresError`) and come back as a 503, which the poller reads as a transient WARNING and resends forever. The route rejects it as the 422 it is, and the converter strips it.
- **Whole request:** one bad item fails the request with a 422. The sender is our own code, so after this table a 422 means the two copies have drifted.

**Storage and dedup (correction 3, confirmed):**
- **The sentinel:** `db.upsert_news` maps a missing ticker at `services/data-engine/db.py:260`, `ticker = item.get("ticker") or MARKET_TICKER`, with `MARKET_TICKER = "_MARKET"` at `db.py:227`. A market row is never written with a NULL ticker.
- **The schema:** `003_context.sql` declares `ticker VARCHAR(10) NOT NULL` (line 9) and `CONSTRAINT news_items_ticker_url_key UNIQUE (ticker, url)` (line 17). `\d data_engine.news_items` on `tradingfirm_dev` (2026-09-10) shows `ticker … not null` and `"news_items_ticker_url_key" UNIQUE CONSTRAINT, btree (ticker, url)`. A NULL could not be stored even by mistake; the insert would raise.
- **Already proven live:** 2.1 checked that two `_MARKET` inserts of one URL leave one row.
- **So** `test_ingest_repeat_batch_is_idempotent` stays on a mocked pool. It asserts the literal `ON CONFLICT (ticker, url) DO NOTHING` and that every row's ticker parameter is `_MARKET`. The real-Postgres proof is the twin round trip's unchanged count.
- **Key normalization** stays inside `upsert_news` (`url.strip()`), the only writer (G1.5). URLs are not canonicalized, so the same article with different tracking parameters becomes two rows. Accepted.

**The rest of the route:**
- **Response:** 200 `{received, sent}`. `sent` counts rows sent, not rows inserted (`executemany`, 2.1).
- **Errors:** no pool, or `DB_ERRORS` / `TimeoutError`, is a 503 `database unavailable`. A mid-batch raise can leave earlier rows stored (2.1's deferred defect), and a resend dedups them.
- **No auth,** like `/scan/run` and `/stock/{t}/refresh`, and port 8001 is published on the host. Accepted for now and carried to the going-public checklist.
- **The dossier is unaffected:** it reads per-ticker news only.

### 6. Transport, risk-shield → data-engine

- **Target:** `settings.data_engine_url`, default `http://data-engine:8001`.
  - The twin hard-codes `http://data-engine-dev:8001`, so it can never write into prod's database.
  - `test_twin_never_ingests_into_prod_data_engine` guards it.
- **Client:** one `httpx.AsyncClient` owned by the poller, with a 10 s hard timeout, no retries and no redirect following.

**Outcomes (correction 2).** Every answer is classified. A poll is a success only when every chunk answered 200 (addition 8):

| answer | log | success |
|---|---|---|
| 200 | INFO with counts | yes, once every chunk answered 200 |
| 422 | **ERROR** on the first, WARNING per slot after (addition 8): the limit copies have drifted (decision 5) | no; the same page fails each slot until fixed, no data lost |
| any other status: 3xx (not followed), 400, 401, 403, 404, other 4xx, 5xx | WARNING with the status | no; the next slot resends the page, and dedup makes that safe |
| transport error or timeout | WARNING with the type | no |

### 7. One poll, in order (`news_poller.poll_once`)

1. **Skip, with no request,** when the key is empty, risk-shield's Finnhub cooldown runs, or data-engine's `tf:cache:finnhub` has a TTL.
2. **One Finnhub call.** A 429 or 401/403 starts risk-shield's cooldown.
3. **Convert** under decision 5, and log the first 3 headlines plus the dropped and truncated counts (G9). An empty page, or one with every item dropped, is a WARNING: no POST, and not a success.
4. **Overlap check** (decision 3) against the previous `lastSuccessAt`, then set `pageSpanMinutes` and `oldestAt` from this page.
5. **POST** the kept items, oldest first, in chunks of at most 200.
6. **Update `news_status`:**
   - `lastPollAt` always
   - `lastSuccessAt`, and `lastError: null`, once every chunk answered 200
   - otherwise `lastError` names the cause

- **Isolation:** a raise out of `poll_once` is caught by the loop (ERROR with the type), and the loop goes on. `CancelledError` propagates.
- **`app.state.news_status`:** `{startedAt, lastPollAt, lastSuccessAt, fetched, sent, dropped, truncated, pageSpanMinutes, oldestAt, lastError, consecutive422}`.
  - *`startedAt` added during commit 4c:* the loop's start, which is addition 8's "the poller's start". Without a start, `newsPollStale` is `null`.
  - *Also changed in 4c:* 3.4's exact-body assertion in `test_market_health_returns_latest_row` gains the three news keys (null with the poller off), next to the payload's.
- **`/health` adds** `newsPollEnabled`, `lastNewsPollAt` (= `lastSuccessAt`), `newsPageSpanMinutes`, `newsOldestAt`, `newsLastError` and `finnhubConfigured`.
- **Shutdown** cancels the news task alongside the scheduler, before the pool and Redis close, with the same 5 s bound.

### 9. `GET /market/calendar?days=7`

- **`days`:** an int, 1–31, default 7. Anything else is a 422.
- **Window:** ET dates from today to `today + days − 1`, inclusive. Today's events stay in the window after they are released, marked `released: true`. From Thu 2026-09-10, `days=7` gives CPI 09-11 and FOMC 09-16.
- **Body:** `{from, to, coversThrough, coverageShort, events: [{date, time, datetimeUtc, type, title, detail, released}]}`, ascending by time.
  - `coverageShort` here is about the window: `to > coversThrough`.
  - The 14-day renewal flag is `/health`'s `calendarCoverageShort`.
- **Coverage:**
  - a window that runs past the coverage → 200 with the events the file has, `coverageShort: true`, and a WARNING
  - a window entirely past the coverage → 200, `events: []`, `coverageShort: true`
  - never a 404
- **An empty window** → 200 with `events: []`.
- **Dependencies:** none (no Postgres, no Redis, no network). `/health` adds `calendarCoversThrough` and `calendarCoverageShort`, both `null` when the file is unavailable, and `/` lists the route.
